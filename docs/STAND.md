## Приборы и поломки

Симулятор слушает Modbus TCP на портах 5020..5023 (линии L1..L4) и отдаёт управляющий API на порту 8090:

```bash
curl localhost:8090/sim/state
curl -X POST localhost:8090/sim/fault -H 'content-type: application/json' \
  -d '{"targetKind":"device","targetId":"RC-104","kind":"silent","ttlSec":120}'
curl -X POST localhost:8090/sim/scenario/night-defrost
curl -X DELETE "localhost:8090/sim/faults?targetId=RC-104&kind=silent"
curl -X DELETE localhost:8090/sim/faults
```

Виды поломок: `silent`, `crc`, `stall`, `exception`, `offline` (порт шлюза закрыт), `power_dip`, `offscale`, `door_stuck`, `defrost`. `GET /sim/state` отдаёт эталон: значения всех приборов, действующие поломки и счётчики запросов по линиям.

`DELETE /sim/faults` без параметров снимает все поломки. Параметры `targetId` (код линии или прибора) и `kind` сужают выбор и сочетаются: фильтр по прибору снимает только поломки, внесённые на сам прибор, а поломки его линии остаются. В ответ приходит число снятых поломок, `{"removed":1}`; неверный фильтр даёт 400.

Время ответа прибора складывается из передачи кадров на скорости линии, постоянной задержки `SIM_TURNAROUND_MS` и случайной добавки до `SIM_TURNAROUND_JITTER_MS` (по умолчанию 40 мс). Добавка чаще всего мала и лишь изредка дотягивает до предела, поэтому у времени ответа длинный хвост, как у настоящих приборов. Последовательность добавок своя у каждой линии и повторяется при том же `SIM_SEED`. Зависший обмен (`stall`) обходится без случайной добавки и ждёт сверх обычного времени `SIM_STALL_MS`.

Сборщик опрашивает все четыре линии и пишет сырые кадры в `fieldstream.telemetry.raw.v1` (ключ это код прибора), итог каждого обращения, в том числе неудачного, в `fieldstream.collector.cycles.v2` (ключ тоже код прибора), а снимок линии с размыкателями, лестницей переподключения и временем ответа в компактируемый `fieldstream.collector.status.v1` (ключ это код линии). Из этих снимков живёт экран Отказы: сборщик стоит за NAT, поэтому его состояние едет топиком, а не запросом к нему. Портов наружу у сборщика нет, состояние воркеров, размыкателей и планов чтения смотрится ещё и изнутри сети:

```bash
docker compose -f infra/compose/docker-compose.yml exec edge-collector wget -qO- 127.0.0.1:8091/internal/lines
```

Процессор разбирает кадр той версией профиля, которой он прочитан, и пишет показания в `ts.readings`, итоги опроса в `ts.poll_cycles`, а состояние приборов в `core.device_state` и в компактируемый топик `fieldstream.device.state.v1`. Кадр, который не разобрать, уходит в `fieldstream.telemetry.raw.dlq.v1` сырыми байтами с исходным ключом, и поток идёт дальше. Минутный агрегат по прибору:

```bash
docker compose -f infra/compose/docker-compose.yml exec timescaledb psql -U fieldstream -d fieldstream \
  -c "select bucket, metric_key, round(avg_value::numeric, 2), n from ts.v_readings_1m where device_id = 1 order by bucket desc limit 9"
```

## Доступ к API

Шлюз слушает 8093 внутри сети, наружу его пути отдаёт nginx на 8080. Учётные записи стенда заводит мигратор, пароль берётся из `DEMO_PASSWORD`: `viewer@fieldstream.local` (только чтение), `engineer@fieldstream.local` (подтверждение алармов, правка уставок, команды линиям, поломки на стенде, запуск сценариев и перепрогонов, повторная подача из очереди недоставленных), `admin@fieldstream.local` (те же права плюс `users.manage`, за которым в шлюзе пока нет ни одной ручки: отдельных административных экранов на стенде нет).

```bash
token=$(curl -s localhost:8080/api/auth/login -H 'content-type: application/json'   -d '{"email":"engineer@fieldstream.local","password":"fieldstream"}' | jq -r .accessToken)

curl -s localhost:8080/api/topology -H "authorization: Bearer $token"          # дерево объектов с состоянием
curl -s localhost:8080/api/devices/RC-101/latest -H "authorization: Bearer $token"
curl -s "localhost:8080/api/devices/RC-101/read-plan?mode=naive" -H "authorization: Bearer $token"
curl -s "localhost:8080/api/alarms?state=active" -H "authorization: Bearer $token"
```

Серия сама выбирает источник по ширине окна и говорит, откуда взяла числа: до шести часов это сырые строки, до недели минутный агрегат, дальше часовой. Источник, шаг и признак обрезки приходят вместе с данными, поэтому подпись под графиком не может разойтись с содержимым:

```bash
from=$(jq -rn 'now - 7*86400 | floor | todate')
to=$(jq -rn 'now | floor | todate')
curl -s "localhost:8080/api/devices/RC-101/series?metrics=supply_temp_c&from=$from&to=$to" \
  -H "authorization: Bearer $token" | jq .meta
# {"source":"readings_1m","bucketMs":360000,"points":1680,"truncated":true, ...}
```

Живой канал это одно соединение на вкладку. Первым кадром приходит приветствие с серверным временем и эпохой, дальше показания, состояния приборов и алармы. При обрыве браузер присылает `Last-Event-ID`, и шлюз либо досылает пропущенное, либо честно требует перечитать всё:

```bash
curl -N "localhost:8080/api/events?keys=device:RC-101&access_token=$token"
```

Команда линии не уходит в брокер прямо из запроса: приём команды это одна вставка в `core.outbox`, а отправкой занимается фоновая рассылка. Охватывающей транзакции вокруг вставки сейчас нет, потому что записывать больше нечего. Применяет её сборщик и отвечает через брокер, в таблицу ответ переносит процессор:

```bash
id=$(curl -s localhost:8080/api/commands -H "authorization: Bearer $token" -H 'content-type: application/json'   -d '{"lineCode":"L1","kind":"line.set_poll_interval","args":{"pollIntervalMs":15000}}' | jq -r .commandId)
curl -s localhost:8080/api/commands/$id -H "authorization: Bearer $token"
# {"stage":"applied","detail":"такт опроса линии L1 теперь 15000 мс", ...}
```

Команда меняет такт у работающего воркера, а не в базе: `GET /api/topology` и `core.lines`
продолжают отдавать такт из описания стенда, а действующее значение видно в снимке линии
(`GET /api/lab/lines`, поле `pollIntervalMs`) и на экране Отказы. После перезапуска сборщика
линия возвращается к такту из описания. То же верно для режима плана чтения и для остановки
линии.

## Засев истории и брокер

Историю на неделю назад заливает одноразовый контейнер: он поднимается вместе со стендом, а
повторить засев можно командой `pnpm stack:seed`. Строки не едут по сети, их порождает сама
база, поэтому неделя на 24 прибора занимает секунды. Повторный запуск ничего не добавляет и не
пишет поверх живых значений. В засеянной истории лежат три происшествия и оттайки по расписанию,
чтобы на экранах было что показывать. Оттайка в засеве идёт двадцать минут каждые шесть часов и
разнесена по приборам, то есть это ровное расписание, а не тот цикл, который крутит живой
симулятор (примерно раз в 55 минут). Длины намеренно разные: засеву нужна предсказуемая картинка
на неделю назад, живому потоку физика.

Kafka доступна с хоста на `localhost:29092`, веб-интерфейс к ней поднимается профилем: `docker compose -f infra/compose/docker-compose.yml --profile tools up -d kafka-ui` (http://localhost:8081).

Поведение самого брокера разобрано отдельно, в [записной книжке по Kafka](kafka-notebook.md):
восемь вопросов и восемь прогонов на живом стенде, которые отвечают на них числами. Опыты
запускает `pnpm --filter @fieldstream/kafka-lab run lab <опыт>` (`order`, `groups`, `rebalance`,
`commits`, `idempotency`, `dlq`, `lag`, `compaction`), без имени команда печатает список. Всё, что
опыт создаёт, называется `fieldstream.lab.<опыт>.*` и убирается в конце прогона даже при отказе,
боевые топики опыты только читают.

Для ежедневной разработки без пересборки образов `pnpm infra:up` поднимает брокер, базу и
применяет миграции, а `pnpm dev` запускает сервисы на хосте в режиме наблюдения за файлами
(переменные берутся из `.env`). В этом режиме фронт живёт на дев-сервере vite (5173) и ходит в
шлюз на 8093, то есть в два origin: `.env` для этого и держит `CORS_ORIGINS`.

## Сценарии стенда

Сценарий стенда проверяет поведение всей системы на живом стенде: вносит настоящую поломку через
симулятор, ждёт, пока сборщик, процессор и шлюз отреагируют как задумано, и снимает поломку.
Сценарии описаны в YAML в `packages/scenarios/scenarios`. Каждый шаг либо вносит или снимает
поломку, либо с пределом по времени ждёт состояния стенда: размыкателя, статуса и режима прибора,
линии, алармов, очереди недоставленных.

Прогон исполняет шлюз, и у кнопки интерфейса и у CI путь один. `POST /api/scenarios/:name/run`
ставит прогон и сразу отвечает 202 с его номером, ход по шагам читается через
`GET /api/scenario-runs/:id`, список сценариев с последними прогонами отдаёт `GET /api/scenarios`.
Запускает инженер или администратор (право `scenarios.run`), смотреть может любой, кому открыт стенд.

```bash
run=$(curl -s -X POST localhost:8080/api/scenarios/dead-device/run -H "authorization: Bearer $token" \
  -H 'content-type: application/json' -d '{}' | jq -r .id)
curl -s localhost:8080/api/scenario-runs/$run -H "authorization: Bearer $token" | jq '.status, [.steps[].status]'
```

Все сценарии по очереди, с ходом шагов в журнале и итоговой таблицей:

```bash
pnpm scenarios:ci                                   # против http://localhost:8080 под engineer@fieldstream.local
SCENARIOS=dead-device,crc-garbage pnpm scenarios:ci
```

Адрес и учётная запись задаются `E2E_BASE_URL`, `E2E_EMAIL` и `E2E_PASSWORD`. Команда завершается
с кодом 1, если хоть один сценарий не прошёл.

Прогон вносит настоящие поломки, поэтому на стенде идёт только один: второй запуск получает 409 с
названием идущего. Сценарий идёт минутами, предел у каждого свой (`timeoutSec`), все шесть подряд
укладываются в 40 минут, и пока прогон идёт, экраны показывают поломку. Внесённые поломки
снимаются при любом исходе. Останавливающийся шлюз отвечает на запуск 503, а идущий прогон
завершает провалом и тоже снимает поломки. После падения шлюза поломки снимет сам стенд по сроку,
а прогон без пульса дольше 30 секунд завершит с ошибкой любой экземпляр шлюза. Размыкатели и линии
пробы берут только из снимков сборщика не старше минуты, а при редком такте опроса не старше трёх
тактов: из двух пределов берётся больший, поэтому на такте 30 секунд снимок остаётся свежим до 90
секунд. Зависший сборщик проваливает пробу, а не подтверждает её старым снимком. Ночную оттайку не отменить: после
`night-defrost-quiet` камеры ещё около 15 минут в оттайке.

## Перепрогон

Перепрогон проверяет правку уставки на сырых кадрах, которые уже лежат в Kafka: процессор
перечитывает кадры окна и дважды пропускает их через движок алармов, с текущими уставками и с
правкой. Ставит прогон инженер или администратор (право `replay.run`), смотреть может любой, кому
открыт стенд. На стенде идёт один прогон, второй запуск получает 409.

Из интерфейса: вкладка Перепрогон, кнопка «Граница испарителя в оттайке +8» выбирает холодильные
камеры и заполняет правку, дальше окно (15 мин, 1 ч, 6 ч, 24 ч или своё) и «Поставить
перепрогон». Номер прогона попадает в адрес страницы (`?run=<id>`), ход, таблица разницы и график
выбранной строки появляются на том же экране. Оттайка в симуляторе начинается примерно раз в 55
минут (40 минут охлаждения, 12 минут нагрева и 3 минуты стока), поэтому окно в 15 минут может не
задеть ни одной, и итогом будет «Правка не изменила ни одного срабатывания». Для примера с
испарителем окно лучше брать от часа.

Через API `POST /api/replay-runs` ставит прогон и сразу отвечает 202 со строкой прогона. Ход
читается по номеру. Разница (`/diff`) и эпизоды одной строки (`/episodes`) есть только у прогона в
статусе `done`: у ждущего, идущего и проваленного 409 с причиной. Список последних прогонов с
идущим сейчас и сроком хранения отдаёт `GET /api/replay-runs`.

```bash
body=$(jq -nc '(now | floor) as $t | {from: ($t - 3600 | todate), to: ($t | todate),
  deviceCodes: ["RC-101", "RC-102"], patches: [{metricKey: "evap_temp_c", mode: "defrost", maxValue: 8}]}')
run=$(curl -s localhost:8080/api/replay-runs -H "authorization: Bearer $token" \
  -H 'content-type: application/json' -d "$body" | jq -r .id)
curl -s localhost:8080/api/replay-runs/$run -H "authorization: Bearer $token" | jq '.status, .progress, .groupId'
until curl -s localhost:8080/api/replay-runs/$run -H "authorization: Bearer $token" \
  | jq -e '.status == "done" or .status == "failed"' >/dev/null; do sleep 2; done   # ждать итога
curl -s localhost:8080/api/replay-runs/$run/diff -H "authorization: Bearer $token" | jq '.changedRules, .rows'
curl -s "localhost:8080/api/replay-runs/$run/episodes?deviceCode=RC-101&metricKey=evap_temp_c&mode=defrost" \
  -H "authorization: Bearer $token" | jq '.baseline, .patched, .truncated'
```

Правка это ключ `metricKey` и `mode` плюс только меняющиеся поля: `minValue`, `maxValue`,
`hysteresis`, `debounceCycles`, `enabled`. `null` снимает границу, пропущенное поле остаётся как
было. Окно старше срока хранения или в будущем, прибор не со стенда и правка, которая не нашла
уставки или ничего не меняет, дают 400 с текстом по-русски.

Пока прогон идёт, на экране Конвейер среди групп потребителей видна временная группа
`fs-replay-<id>` с одним участником на партициях сырого топика. Смещений она не подтверждает, а
после итога процессор её удаляет. Смещения боевой группы `fs-processor` при этом не двигаются.
Короткое окно процессор может дочитать раньше, чем шлюз обновит снимок брокера, и тогда группа на
экран не попадёт.

Перепрогон выключается у процессора переменной `REPLAY=off` (compose передаёт сервисам `.env`,
после правки `docker compose -f infra/compose/docker-compose.yml up -d --no-deps stream-processor`,
а после `pnpm stack:scale` ещё и с `--scale stream-processor=2`). Выключенный процессор прогоны не
забирает и пишет об этом в журнал при старте. Поставленный прогон остаётся в очереди, экран через
пять секунд ожидания объясняет почему, а спустя `REPLAY_QUEUE_TIMEOUT_MS` (переменная шлюза, по
умолчанию 60 секунд) шлюз снимает его с ошибкой «ни один процессор не забрал прогон: перепрогон
выключен или процессор не запущен». Снимает при следующем чтении списка или постановке нового
прогона, иначе такой прогон занимал бы стенд навсегда.

У процессора настраиваются такт забора `REPLAY_POLL_MS` (2 с), пульс `REPLAY_HEARTBEAT_MS` (2 с),
срок `REPLAY_STALE_MS` (60 с), после которого прогон без пульса завершает любой свободный
экземпляр, и предел длительности прогона `REPLAY_MAX_MS` (10 минут).

На свежем стенде кадры есть только с момента подъёма, поэтому длинное окно покрыто лишь частично. Засев кладёт неделю истории прямо в базу, а в Kafka лежат
только кадры, которые сборщик отправил сам, и не старше семи суток. Том брокера `kafka-data`
переживает `pnpm stack:down`, поэтому после перезапуска в топике остаются и кадры прошлых запусков,
с дырой на время простоя. Окно за 24 часа на стенде, впервые поднятом час назад, прочитает около
часа кадров, и экран скажет об этом строкой покрытия. Окно, которое кончилось больше чем за пять
минут до первого кадра в топике, завершится сразу, с пометкой «В окне нет кадров». Кадры старше
семи суток брокер удаляет сам, поэтому такое начало окна шлюз не принимает.

## Проверки

Сценарии Playwright идут против поднятого стенда:

```bash
pnpm --filter @fieldstream/web e2e                          # против http://localhost:8080
E2E_BASE_URL=http://127.0.0.1:5173 pnpm --filter @fieldstream/web e2e
```

По умолчанию сценарии берут установленный Chrome, чтобы не качать браузер ради локального
прогона. Пустая `E2E_CHANNEL` переключает их на браузер, который ставит сам Playwright.

Рядом с проверками на поднятом стенде живут два инструмента, которые ничего не утверждают, а
показывают: `pnpm bench` снимает восемь замеров и к каждой цифре печатает команду повтора
(раздел [Замеры](#замеры)), а `pnpm --filter @fieldstream/kafka-lab run lab <опыт>` гоняет восемь
опытов с Kafka на своих учебных топиках, с разбором в [записной книжке](kafka-notebook.md).

Проверки собраны в два потока. Быстрый идёт на пуш в `main` и в ветки `stage-*`, на запрос
слияния в `main` и по кнопке: сборка, типы, линтер, формат, границы зависимостей, модульные тесты
и сверка конфига топиков с манифестом. Тяжёлый поднимает настоящие Kafka, TimescaleDB и весь
стенд в Docker, поэтому идёт на запрос слияния в `main`, на пуш в `main`, ночью по расписанию и по
кнопке: интеграционные тесты, сценарии стенда через шлюз и сценарии интерфейса против контейнера.

## Замеры

Числа снимает `pnpm bench` (`tools/bench`) с поднятого стенда. Замеров восемь: `throughput` (темп
записи показаний в `ts.readings` против расчётного по топологии), `latency` (задержка кадра до
события живого канала), `lag` (отставание боевых групп потребителей), `memory` (память и процессор
контейнеров), `images` (размеры образов), `volumes` (размеры томов), `compression` (сжатие кусков
`ts.readings`), `query` (запрос серии под `EXPLAIN ANALYZE` по всем трём источникам). Без имён
снимаются все восемь, имена сужают прогон, `-h` печатает список.

```bash
pnpm bench                        # все восемь замеров
pnpm bench memory volumes images  # только названные
pnpm bench --out bench.md         # ещё и таблицей Markdown в файл
pnpm bench --load --load-ms 1000  # с наведённой нагрузкой, такт возвращается сам
```

Каждая строка отчёта печатается вместе с командой, которой ту же цифру берут руками: запрос к базе,
обращение к шлюзу или вызов docker. Без `--load` инструмент стенд не меняет: только выборки из базы
под читающей ролью `fs_api`, чтение метаданных брокера и чтение состояния docker, а заведённая
входом сессия шлюза закрывается в конце прогона. Ключ `--load` на время замеров переводит линии на
частый такт штатной командой `line.set_poll_interval` и возвращает прежний такт и при срыве замера,
и при снятии прогона с клавиатуры. Адрес шлюза и учётная запись берутся из `BENCH_BASE_URL`,
`BENCH_EMAIL` и `BENCH_PASSWORD`, замерам по базе (`throughput`, `compression`, `query`) нужен
пароль читающей роли в `FS_API_PASSWORD`.

Память это мгновенный снимок `docker stats` без усреднения, поэтому она плавает от прогона к
прогону и растёт вместе с временем жизни стенда. Предел памяти в compose задан только брокеру
(1 ГиБ), и на этом снимке он занял 80 % своего предела; остальные контейнеры видят память хоста.
Сумма размеров образов номинальная: общие слои базового образа посчитаны в каждом образе, на диске
все они вместе занимают меньше. Тома тоже растут вместе с временем жизни стенда, поэтому их размер
берётся прогоном `pnpm bench volumes`, а не переносится из документа в документ: в других разделах
на эту строку стоит ссылка.

Задержка меряется сквозным путём сборщик, Kafka, процессор, шлюз, живой канал, и в неё входит такт
дросселя событий (одно событие на прибор в секунду), поэтому хвост распределения гуляет от прогона
к прогону сильнее середины: p99 в соседних прогонах выходил и 9, и 28 мс.
