# 0003. Схемы zod в общем пакете вместо реестра схем и Avro

## Контекст

Одни и те же данные проходят через четыре кодовые базы: сборщик кладёт кадр в Kafka, процессор
его разбирает и пишет в базу, шлюз отдаёт наружу, браузер рисует. Девять топиков и три десятка
ответов HTTP, и форму каждого иначе пришлось бы описывать по четыре раза. Цена расхождения тут
не ошибка сборки, а тихий мусор: кадр с полем не того типа доедет до вставки в гипертаблицу и до
графика. Значит, форма проверяется на границе, а не подразумевается.

## Решение

Пакет `packages/contracts`: полторы сотни схем zod и выведенные типы, зависимость ровно одна, сам
`zod`. На него ссылается каждый сервис и фронт, поэтому чужая зависимость стала бы общей: лист
закреплён правилом `contracts-are-leaf`.

Топики описаны в `src/kafka/topics.manifest.ts`: `keyOf` задаёт порядок внутри прибора, срок
хранения оплачивается диском брокера. Мажорная версия живёт в имени топика: смена ключа
партиционирования разводит старых и новых потребителей по разным топикам вместо тихой
рассортировки.

`decodeMessage` даёт четыре класса отказа: `empty`, `invalid_json`, `schema`,
`schema_major_mismatch`, причём версию читает из заголовка до разбора тела. Снаружи так же: шлюз
проверяет через `safeParse` запросы, а фронт каждый ответ в `shared/api/endpoints.ts`.

## Последствия

- Форма правится в одном месте: тип во фронте это `z.infer` той же схемы, которой шлюз проверяет
  запрос.
- JSON платится размером, у сырых кадров это гасится gzip на брокере: kafkajs распаковывает его
  без стороннего кодека.
- zod уезжает в браузер вместе с пакетом схем: пара сотен килобайт исходников в карте бандла.
  Фронт парсит каждый ответ, значит платит за это весом.
- Машинной проверки совместимости нет, поднять `v` никто не заставляет. Зато схемы объявлены
  `.strict()`: новое поле старый потребитель отвергнет с классом `schema`, а не пропустит мимо.
- Очередь недоставленных заведена под сырые кадры: их байты с исходным ключом сохраняются и
  возвращаются в топик. В прочих потоках неразобранное сообщение пропускается, местами молча.

## Отвергнутые альтернативы

**Confluent Schema Registry с Avro.** Даёт ровно то, чего здесь нет: проверку совместимости при
публикации схемы. Платить пришлось бы вторым контейнером на JVM рядом с брокером, которому и так
отданы полгигабайта кучи, и шагом сборки для генерации классов.

**Protobuf.** Та же генерация, плюс `.proto` отдельным языком рядом с TypeScript. Жаль и
читаемости: сейчас тело сообщения видно глазами в `kafka-ui`, без дескриптора и декодера.

**Форма без исполняемой проверки.** JSON Schema не привязана к Node, но типы пришлось бы выводить
генератором, а проверки сложнее формы туда не кладутся: `superRefine` уставки требует `minValue`
меньше `maxValue`. Голые типы TypeScript дешевле и на границе бесполезны: `as TelemetryRaw`
компилятор пропустит для любых байтов, не дав ни класса отказа, ни повода его записать.
