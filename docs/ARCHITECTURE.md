## Задача

Собирать телеметрию с промышленных приборов, которые опрашиваются по Modbus, хранить историю, считать по ней алармы и показывать всё это в реальном времени в браузере.

Задача звучит просто ровно до момента, когда выясняется, что приборы отвечают медленно, иногда не отвечают вовсе, а иногда отвечают мусором; что физическая линия связи одна на десяток приборов; что история растёт на миллионы строк в сутки и её всё равно надо показывать графиком за месяц; и что «авария» это не булево значение, а состояние, зависящее от режима работы объекта.

Система поднимается одной командой и не требует железа: приборы эмулирует отдельный сервис, говорящий по настоящему протоколу.

## Предметная область

Демо-стенд это сеть холодильного оборудования: холодильные камеры и учёт электроэнергии на двух площадках.

### Физика

Холодильные контроллеры и счётчики электроэнергии подключены по RS-485 к Ethernet-шлюзам. Шлюз отдаёт Modbus TCP.

RS-485 это разделяемая линия. Параллельные запросы в неё физически недопустимы: два одновременных кадра сталкиваются, и приёмник получает мусор. Отсюда следует главное ограничение всей системы: **на линию приходится ровно один последовательный цикл опроса**. Из этого ограничения растут воркер на линию, три предохранителя от зависания и размыкатель на конкретный прибор.

Второе физическое ограничение это скорость. На 9600 бод кадр Modbus передаётся за десятки миллисекунд, и разница между 11 запросами и 3 запросами на прибор становится разницей между укладыванием в такт опроса и неукладыванием.

### Иерархия объектов

```
Site (SITE-A, SITE-B)
 └─ Gateway (GW-01, GW-02, адреса из 192.0.2.0/24)
     └─ Line (L1..L4, baud 9600/19200, опрос 10 с, таймаут 600 мс)
         └─ Device (slaveId 1..6, по шесть приборов на линию)
```

Итого 24 прибора, 4 линии, 2 шлюза, 2 площадки.

### Модели приборов

Заведены две модели.

| Профиль                             | Коды             | Особенности кодирования                                                           |
| ----------------------------------- | ---------------- | --------------------------------------------------------------------------------- |
| `rc-2000`, холодильный контроллер   | `RC-101..RC-112` | знаковый `int16` со `scale` 0.1, битовая маска аварий, перечисление состояний     |
| `pm-3phase`, счётчик электроэнергии | `PM-201..PM-212` | `float32` и `uint32`, разные порядки слов у разных параметров, монотонный счётчик |

Прибор описан **данными**, а не кодом: секции, параметры с адресом, типом, порядком байтов, множителем, точностью. Исполняет описание один общий движок. Добавление модели прибора это один файл и ноль правок в сервисах.

### Режимы работы и уставки

У камеры есть режимы `cooling`, `defrost`, `service` и `off`. Во время оттайки температура законно растёт на шесть и более градусов.

Если уставку хранить парой чисел на параметр, аларм по верхней границе будет срабатывать на всём складе на каждой оттайке, и его отключат в первый же день. Поэтому уставка хранится по ключу `(прибор, метрика, режим)`, а в режимах `service` и `off` алармы заглушены: холодная или обслуживаемая камера иначе выдаёт аварию по всем параметрам сразу.

## Схема системы

```
  +---------------------------------------------------------------+
  |                    Docker network: fieldstream                |
  +---------------------------------------------------------------+

   [device-sim]              Modbus TCP (порты 5020..5023)
   4 TCP-сервера,      <---------------------------------+
   24 прибора, 6 на линию,                               |
   API инъекции поломок <--- HTTP ---+                   |
                                     |          +----------------+
                                     |          | edge-collector |
                                     |          | 4 LineWorker,  |
                                     |          | размыкатель,   |
                                     |          | план чтения    |
                                     |          +----------------+
                                     |              |         ^
                                     |     сырые    |         | команды
                                     |     кадры    v         |
  +------ KAFKA (KRaft, 1 брокер), имена без префикса fieldstream. ------+
  |                                                                      |
  |  telemetry.raw.v1             key=deviceCode   6p   7 суток          |
  |  collector.cycles.v2          key=deviceCode   6p   3 суток          |
  |  collector.status.v1          key=lineCode     3p   COMPACT          |
  |  telemetry.readings.v1        key=deviceCode   6p   24 часа          |
  |  device.state.v1              key=deviceCode   3p   COMPACT          |
  |  alarms.events.v1             key=deviceCode   3p   30 суток         |
  |  device.commands.v1           key=siteCode     3p   7 суток          |
  |  device.commands.results.v1   key=commandId    3p   COMPACT          |
  |  telemetry.raw.dlq.v1         key=исходный     1p   14 суток         |
  +----------------------------------------------------------------------+
        ^                        |    |                        ^
        |                        v    v                        |
        |                 +------------------+                 |
        |                 | stream-processor |                 |
        |                 | декодирование,   |                 |
        |                 | алармы, здоровье |                 |
        |                 +------------------+                 |
        |                        |                             |
        |            батч INSERT ON CONFLICT DO NOTHING        |
        |                        v                             |
        |         +--------------------------------------+     |
        |         |  PostgreSQL 16 + TimescaleDB         |     |
        |         |  схемы core и ts, три роли           |     |
        |         |  ts.readings -> _1m -> _1h           |     |
        |         +--------------------------------------+     |
        |                        ^                             |
        |                 SELECT |                             |
        |                        |                             |
        |                  +----------------+                  |
        +------------------| api-gateway    |------------------+
                           | REST + SSE     |
                           +----------------+
                                  ^  |
                       HTTP /api  |  | SSE /api/events
                                  |  v
                           +----------------+
                           |  nginx (web)   |  :8080
                           +----------------+
                                  ^
                             браузер (React 19 SPA)
```

Kafka используется только между сервисами. Сборщик не знает адреса процессора, процессор не знает адреса API. Браузер общается с системой по HTTP и SSE через nginx, то есть в одном origin, без возни с CORS и cookie.

Ни один внутренний сервис не публикует порты наружу: у `edge-collector`, `stream-processor` и `api-gateway` в базовом compose нет секции `ports` вообще. Порт шлюза открывается только оверрайдом для разработки, и то на `127.0.0.1`.

В конфигурации входа (`infra/nginx/nginx.conf`) четыре неочевидных места. Префикс `/api` не срезается при проксировании: он принадлежит самому шлюзу, и по этому же пути лежит кука обновления (`path=/api/auth`), так что обрезка префикса молча разлогинивала бы вкладку при каждой перезагрузке. У потока событий своя локация с выключенной буферизацией и часовым тайм-аутом чтения: заголовки потока уходят вместе с первым кадром, поэтому буферизация ломает не задержку, а само установление канала, а тайм-аут меньше паузы между keepalive рвал бы соединение на ровном месте. Соединение к шлюзу переиспользуется с тайм-аутом короче `keepAliveTimeout` fastify, иначе шлюз закрывал бы его ровно в момент отправки следующего запроса. Наконец, маршруты приложения отдаются оболочкой через `try_files`, а сама оболочка помечена `no-store`: иначе заход прямо на `/device/RC-101` давал бы 404, а после обновления стенда вкладка продолжала бы просить файлы предыдущей сборки.

За обратным прокси адрес запроса это адрес прокси, поэтому шлюз в контейнере поднимается с `TRUST_PROXY=on`: без этого все входы попадали бы в одно ведро ограничителя попыток, а в журнале сессий у всех стоял бы один и тот же адрес.

## Границы сервисов

Отдельный процесс заводится, только если у него выполняется хотя бы одно из трёх условий: **своё место запуска**, **свой профиль нагрузки** или **своя зона отказа**.

По этому правилу выделены четыре:

| Сервис             | Почему отдельный                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `device-sim`       | стенд, а не часть продукта, и намеренно ломается                                         |
| `edge-collector`   | стоит в сети площадки, наружу только исходящее соединение к брокеру                      |
| `stream-processor` | масштабируется по числу партиций, обязан уметь переигрывать историю независимо           |
| `api-gateway`      | масштабируется по числу пользователей, его латентность нельзя связывать с приёмом данных |

Отдельно не выделены:

- Движок алармов живёт внутри `stream-processor`: у него тот же вход, тот же такт и та же зона отказа. Отдельный сервис добавил бы сетевой вызов и ничего больше.
- Роллапы делает сама база через continuous aggregates. Сервис агрегации не нужен.
- Авторизация живёт внутри `api-gateway`. Приложение одно, обмениваться удостоверениями не с кем.

## Состав сервисов

### device-sim

Заменяет железо. Поднимает 4 Modbus TCP сервера, по одному на линию, и держит на каждом шесть slave-адресов: всего 24 прибора.

Карта регистров строится **из тех же профилей приборов**, что использует сборщик, и значения кодируются **тем же кодеком**, которым потом декодируются. Благодаря этому round-trip тест ловит ошибку в обе стороны сразу, а новый прибор начинает симулироваться сразу после появления файла профиля.

Физика детерминирована сидом: суточная кривая нагрузки, тепловая модель камеры, цикл оттайки примерно раз в 55 минут (40 минут охлаждения, 12 нагрева и 3 стока), гистерезис компрессора, монотонные счётчики. Значения меняются плавно, шагом заведомо меньше порога фильтра скачков, поэтому фильтр не срабатывает ложно.

Задержка ответа считается по реальному времени кадра на заявленной скорости линии: `delayMs = bytes * 11 / baud * 1000 + turnaround`. Без этого выигрыш блочного чтения остался бы теоретическим, а так он виден на графике длительности цикла.

Отдельный API позволяет вносить неисправности: молчащий прибор, искажённый кадр, зависший обмен, исключение протокола, провал напряжения на линии, уход значения за шкалу, залипшая дверь, обрыв шлюза целиком и принудительная оттайка. Последнюю через шлюз не внести: схема запроса её отклоняет, потому что оттайка приходит сценарием стенда, а не ручкой поломок.

Сервер Modbus TCP в симуляторе свой и небольшой: разбор заголовка MBAP и чтение регистров функциями 3 и 4. Готовая серверная реализация сама собирает кадр ответа, а стенду нужно отдавать искажённые кадры, молчать, зависать и закрывать порт шлюза. Запросы со всех соединений к одной линии встают в общую очередь, как на настоящей шине. Совместимость проверяется тестом, в котором сервер опрашивает та же клиентская библиотека, что стоит в сборщике.

Симулятор это отдельный процесс: в боевом коде нет ни одной ветки «если тест», и путь проверяется целиком, включая сеть, таймауты и переподключения.

### edge-collector

Единственный сервис, который трогает приборы. На каждую линию ровно один `LineWorker` с бесконечным последовательным циклом: следующий обход планируется только после завершения предыдущего, поэтому очередь опросов не накапливается.

Линии делятся между сборщиками переменной `COLLECTOR_LINES`: сборщик поднимает воркеры только своих линий и команды к чужим молча пропускает. На стенде переменная пустая, и один сборщик ведёт все четыре линии.

**Три независимых предохранителя от зависания:**

1. Мягкий таймаут запроса. Его приносит описание линии (`requestTimeoutMs` в `packages/contracts/src/topology/stand.ts`), на стенде это 600 мс; переменной окружения у него нет.
2. Собственный жёсткий таймаут `timeout * 2 + 250` через гонку промисов. Нужен потому, что клиентская библиотека умеет зависать так, что промис не резолвится никогда. При срабатывании клиент помечается на пересоздание.
3. Сторожевой таймер всего цикла, `max(pollInterval * 6, 5 минут)`, с принудительным разрывом соединения.

**Размыкатель по ключу `линия:адрес`.** После двух отказов подряд источник уходит на редкую пробу: 30 секунд, удвоение, потолок 5 минут. Перед обходом воркер спрашивает, можно ли вообще идти в эту линию. Смысл в том, что один мёртвый прибор иначе съедает таймаут на каждом обходе и растягивает цикл для всех живых соседей.

**Переподключение** с экспоненциальной задержкой от 1 до 30 секунд и джиттером плюс-минус 10 процентов, чтобы линии не синхронизировались между собой. Фактически выбранная задержка публикуется событием, поэтому лестницу задержек можно нарисовать по фактам, а не по формуле.

**При недоступности Kafka опрос не прерывается.** Сообщения копятся в буфере на 2000 штук (`COLLECTOR_BUFFER_CAPACITY`), при переполнении отбрасываются самые старые. На стенде это около шести минут потока: за обход линии уходят шесть кадров, шесть итогов опроса и два снимка линии, четыре линии с тактом 10 секунд дают примерно 5.6 сообщения в секунду. Терять телеметрию осознанно лучше, чем расти в памяти до отказа процесса.

Сборщик публикует **сырой кадр** и ничего не знает ни про базу, ни про декодирование в физические величины, ни про алармы.

**Снимок линии едет отдельным компактируемым топиком.** В `fieldstream.collector.status.v1` уходит состояние линии: размыкатели по приборам, лестница переподключения, сторож обхода, время ответа с перцентилями, режим плана и действующий такт опроса. Снимок публикуется в начале и в конце обхода, при остановке воркера и сразу после команды, сменившей такт или режим плана. Ключ это код линии, поэтому компакция держит последний снимок каждой из них. Сборщик стоит за NAT и портов наружу не открывает, так что экран Отказы и пробы сценариев стенда читают именно эти снимки через шлюз.

### stream-processor

Единственный писатель телеметрии. Читает сырые кадры, декодирует по версии профиля, зафиксированной в самом кадре, применяет множители и порядок байтов, фильтрует резкие скачки, определяет режим камеры, ведёт дерево здоровья, гоняет движок алармов и пишет батчами в гипертаблицы. Производных величин он не считает: в базу ложатся ровно те метрики, которые отдал декодер, а перегрев `superheat_k` приходит с прибора отдельным регистром, а не считается разностью температур.

Ядро вынесено в чистые функции без ввода-вывода:

```ts
evaluateDeviceAlarms({ deviceCode, mode, metrics, rules, prevState, nowMs });
detectDeviceEvents(prev, curr);
buildHealthTree({ site, policy, startedAtMs, nowMs });
spikeFilter(state, value, { maxDelta, acceptAfter });
```

Ноль побочных эффектов, время приходит аргументом. Именно это делает возможным переигрывание истории: тот же код, другой источник и другой приёмник.

**Дерево здоровья** отдаёт не плоский список «жив или мёртв», а иерархию с машинной причиной статуса: `consecutive_errors`, `stale`, `no_data`, `awaiting_success`, `startup_grace`, `polling_disabled`, `children_offline`. Причина `polling_disabled` деревом поддержана, но живой поток её не выставляет, и почему так, сказано в разделе [Решения и компромиссы](#решения-и-компромиссы).

Правило агрегации у шлюза намеренно отличается от правила у линии. Если все линии шлюза молчат, шлюз получает статус `unknown`, а не `offline`, потому что по молчанию линий нельзя судить о живости самого шлюза. Асимметрия неочевидна, поэтому закрыта отдельным именованным тестом.

Окно `startup_grace` длиной 70 секунд нужно, чтобы после перезапуска дерево не мигало красным: молчание в первые секунды это ещё не авария.

Состояние прибора публикуется в компактируемый топик `device.state.v1` и пишется в `core.device_state` только при смене статуса, причины или режима, а не на каждом такте. Режим камеры выводится из состояния оттайки в самом кадре.

**Масштабирование.** Процессор можно запустить в нескольких экземплярах, и данные одного прибора всё равно обрабатывает ровно один из них. Сырые кадры и циклы опроса разложены одним ключом, кодом прибора, по одинаковому числу партиций, поэтому кадры и циклы прибора лежат в партициях с одним номером. Оба топика читает одна группа `fs-processor` со своим назначателем партиций: участники сортируются по идентификатору, и партиция с номером N любого топика достаётся участнику N по кругу. Стандартный назначатель kafkajs раскладывает партиции всех топиков одним сплошным списком и такой гарантии не даёт.

Экземпляр владеет прибором, если ключ прибора ведёт в одну из его партиций сырых кадров. Номер партиции считает тот же разделитель kafkajs, которым пишет продюсер, поэтому расчёт не может разойтись с тем, куда кадр лёг на самом деле. До первого вступления в группу экземпляр не владеет ничем и ничего не публикует, а проверка здоровья отдаёт состояние и события только своих приборов. Дерево для агрегации по-прежнему строится по всему стенду.

При ребалансе состояние прибора переезжает вместе с партицией. Отдельного события об отзыве партиций в kafkajs нет, приходит только новое назначение, поэтому разница считается между назначениями. Если потребитель упал или остановился, либо экземпляр вернулся в группу под новым идентификатором участника, все прежние приборы считаются отобранными: пока его не было, их мог вести другой экземпляр, и даже та же раскладка после возвращения требует восстановления. У отобранных приборов из памяти сразу уходят алармы, фильтры скачков и трек здоровья. Новые получают из базы открытые эпизоды алармов и последнее записанное состояние, а фильтры скачков у них начинаются с чистого листа. Пачки ждут окончания этой загрузки, иначе первая пачка новой партиции прошла бы без восстановленных эпизодов. Каждая попытка чтения ограничена по времени, и все попытки вместе заметно короче таймаута сессии, чтобы экземпляр не вылетел из группы, пока ждёт базу. Восстановление при старте процесса больше не нужно, первое назначение и есть старт.

Если база так и не ответила, экземпляр пишет об этом в журнал и работает без восстановления, и цена у этого есть. Прежние открытые эпизоды этих приборов остаются в базе незакрытыми до ручного снятия, а по той же метрике может открыться повторный эпизод. Здоровье начинается с нуля, но такой прибор не публикуется, пока статус не выяснится по первому успешному циклу или по концу окна `startup_grace`, отсчитанного от момента переезда. Иначе догадка затёрла бы в базе и в топике настоящее состояние, записанное прежним владельцем.

Проверка здоровья прежнего владельца может совпасть по времени с чтением состояния у нового. Чтобы чтение не проскочило мимо записи, которая уже идёт, оба берут одну рекомендательную блокировку PostgreSQL (advisory lock): проверка здоровья пишет под общей, новый владелец читает под исключительной. Уже под блокировкой проверка смотрит, не начался ли ребаланс и свой ли ещё прибор. С начала ребаланса и до конца переезда экземпляр здоровье не публикует вовсе.

Восстановленный прибор не порождает ложных событий. Строка состояния в базе переписывается только при смене статуса, причины или режима, поэтому время последнего успеха у давно живого прибора старое, и online из базы считается подтверждённым на момент переезда. Иначе первая же проверка объявила бы прибор протухшим, а следующий цикл вернул бы его в сеть событием, которого не было. Дверь и оттайка после переезда неизвестны, режим из базы тоже не повод объявлять его смену, так что точкой отсчёта становится первый кадр нового владельца.

От раздельных групп для кадров и циклов отказались. Раньше циклы читала своя группа по ключу линии, и две группы раскладывали партиции независимо: кадры прибора уходили в один экземпляр, циклы в другой, а проверка здоровья в каждом публиковала состояние всех приборов по половине картины. Одного общего ключа при двух группах тоже мало, потому что одинаковые номера партиций ничего не дают, если назначения групп никак не связаны. Смена ключа и числа партиций у топика циклов ломает совместимость, поэтому топик получил новую версию в имени.

**Перепрогон уставок** тоже исполняет процессор: забирает запрос из `core.replay_run`, перечитывает сырые кадры окна временной группой `fs-replay-<id>` и гонит их через те же `processFrame` и `evaluateFrameAlarms`, что живой поток, с двумя наборами уставок. Выключается переменной `REPLAY=off`. Устройство описано в разделе [Переигрывание истории](#переигрывание-истории).

### api-gateway

Всё, что видит браузер: авторизация и права, дерево объектов, история серий, алармы и уставки, шина живых событий, отправка команд приборам (только через API: экрана команд в интерфейсе нет), панель готовности стенда до входа, снимок конвейера с очередью недоставленных, ручки стенда поломок, сценарии и перепрогон.

Телеметрию не пишет вообще: у роли `fs_api` нет прав на вставку в `ts.readings`, и это проверяется интеграционным тестом, а не соглашением.

**Авторизация с разделением токенов.** Access-токен живёт в памяти вкладки, refresh в куке `HttpOnly` с узким путём. В базе хранится не токен, а его хеш с секретной солью. Ротация идёт атомарным обновлением по предыдущему хешу: проигравший гонку запрос получает ноль строк и честный отказ, а не порчу состояния. Окно повтора длиной 60 секунд решает частую беду: если ответ потерялся в сети и клиент повторил тот же refresh, он получает ту же пару токенов, а не разлогинивание. Отдельно различаются «сессия отозвана» и «сервер недоступен»: во втором случае пользователя не выбрасывает.

**Живые события через SSE**, одно соединение на вкладку. Маршрутизация по ключам подписки: каждому событию шлюз ставит сразу три, `device:RC-101`, `line:L1` и `site:SITE-A`, так что подписаться можно на любом уровне. Кольцевой буфер последних событий с монотонным идентификатором: при обрыве браузер присылает `Last-Event-ID`, сервер добивает пропущенное. Если идентификатор вышел за пределы кольца или инстанс перезапустился, отправляется явный сигнал рассинхронизации, и клиент делает один полный перезапрос вместо тихой потери данных.

Два места в потоке событий ломаются незаметно. Первое: заголовки потока событий снимаются один раз, синхронно, до первого события, поэтому заголовок с серверным временем ставится хуком на входе запроса. Поставленный перехватчиком, он в поток уже не попадает, и это не видно никак, кроме отсутствующего заголовка. Второе: сжатие ответов надо отключать именно для потока событий, причём по исходному URL запроса, потому что к моменту отправки заголовков путь уже обрезан роутером; сейчас плагин сжатия не подключён вовсе, и это записано здесь, чтобы его не включили бездумно. На стороне nginx у потока событий должна быть отключена буферизация, иначе события копятся и приходят пачками раз в минуту.

Браузерный `EventSource` не умеет ставить заголовки, поэтому поток принимает токен и параметром строки запроса. Транспорт умеет сужать подписку параметром `keys` до нужных приборов, линии или площадки, и тогда экран прибора не получает поток всей площадки. Само приложение этим не пользуется и держит одно соединение на вкладку на всё, что разрешено правами (`useLivePatch([])` в `apps/web/src/app/AppLayout.tsx`): на стенде из 24 приборов сужать нечего, а экраны переключаются чаще, чем окупилось бы переподключение. Сужение ключами при этом закрыто юнит-тестом живого канала. События фильтруются по правам: у кого нет доступа к приборам, тот не получит их показаний, даже подписавшись.

**Ограничитель попыток входа живёт в таблице, а не в памяти процесса**: перезапуск шлюза не обнуляет счётчик. Платят только неудачные попытки, поэтому обычная работа в него не упирается, а подбор пароля упирается. Ведро адреса шире ведра почты: за одним адресом может сидеть целая площадка.

**Команды приборам идут через очередь исходящих.** Из запроса в брокер не уходит ничего: приём команды это одна вставка в `core.outbox`, а отправку делает фоновая рассылка, поэтому недоступный брокер не роняет запрос. Охватывающей транзакции вокруг вставки сейчас нет, потому что записывать больше нечего; когда рядом появится вторая запись, она ляжет той же транзакцией, и сообщение в топике не сможет разойтись с состоянием базы. Повторная публикация безвредна. Сборщик про базу не знает, он стоит за NAT, поэтому факт применения едет обратно отдельным компактируемым топиком, а в таблицу его переносит процессор.

**Единая шкала времени.** Сервер ставит своё время в заголовок каждого ответа, клиент подводит часы с поправкой на время обращения. Весь интерфейс спрашивает «сейчас» только у этого модуля, а правило линтера запрещает обращаться к системным часам напрямую где-либо ещё. При расхождении часов в десять минут свежие данные выглядят протухшими, а протухшие свежими.

**Перепрогон шлюз ставит и читает, но не исполняет.** Схема контрактов проверяет форму запроса: окно не длиннее срока хранения сырого топика, до 24 приборов и до 20 правок, без повторов. Затем шлюз по своим часам проверяет, что начало окна не старше срока хранения, а конец не в будущем (допуск минута), и что приборы есть в топологии; пока топология не прочитана, ответ 503. Шлюз читает уставки выбранных приборов, накладывает правку и кладёт оба снимка в строку прогона, а в брокер не пишет ничего. Разницу он считает агрегатом в базе, не выгружая эпизоды, и читает прогон вместе с итогом одним снимком `REPEATABLE READ`: иначе чистка старых прогонов между двумя запросами дала бы пустой итог вместо 404.

## Kafka

### Топики

Все имена, ключи, число партиций и настройки объявлены **один раз** в `packages/contracts/src/kafka/topics.manifest.ts`. Из манифеста выводятся и конфигурация создания топиков, и типы сообщений. Манифест это код, а не документация про код, поэтому разойтись с реальностью он не может.

| Топик                        | Ключ и почему                                                                                                                                                                 | Партиций | Хранение       |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------- |
| `telemetry.raw.v1`           | `deviceCode`. Порядок нужен только внутри прибора. Ключ это стабильный бизнес-код, а не идентификатор из базы: пересоздание базы иначе переразбросало бы приборы по партициям | 6        | 7 суток        |
| `collector.cycles.v2`        | `deviceCode` и столько же партиций, как у сырых кадров: цикл прибора ложится в партицию с тем же номером, что и его кадры                                                     | 6        | 3 суток        |
| `collector.status.v1`        | `lineCode`: снимок линии целиком, поэтому ключ это линия, а не прибор. Компакция хранит последний снимок каждой линии                                                         | 3        | компактируется |
| `telemetry.readings.v1`      | `deviceCode`                                                                                                                                                                  | 6        | 24 часа        |
| `device.state.v1`            | `deviceCode` как идентификатор узла                                                                                                                                           | 3        | компактируется |
| `alarms.events.v1`           | `deviceCode`: важен порядок «поднят, затем снят» внутри прибора, а не глобальный порядок по правилу                                                                           | 3        | 30 суток       |
| `device.commands.v1`         | `siteCode`, команды одной площадке применяются по порядку                                                                                                                     | 3        | 7 суток        |
| `device.commands.results.v1` | `commandId`: ответ исполнителя нужен ровно один, последний                                                                                                                    | 3        | компактируется |
| `telemetry.raw.dlq.v1`       | сохраняется ключ исходного сообщения, иначе после повторной подачи оно уедет в другую партицию и порядок внутри прибора развалится                                            | 1        | 14 суток       |

В сыром топике едут **сырые слова регистров**, а не готовые значения. Только так историю в принципе можно переиграть исправленным декодером, хотя сейчас [перепрогон](#переигрывание-истории) меняет только уставки.

Топик `telemetry.readings.v1` живёт сутки, потому что это шина живого распределения, а не хранилище. Источник истины по истории это гипертаблица.

Компактируемых топиков три, и читают их по-разному. Снимки линий и ответы на команды читаются с начала, и там компакция делает ровно то, ради чего выбрана: поднявшийся шлюз получает последний снимок каждой линии, а процессор последний ответ по каждой команде, не перечитывая журнал. Состояние приборов мост шлюза читает только с конца, а процессор при переезде партиций поднимает его из Postgres, а не из топика. Для `device.state.v1` компакция поэтому держит журнал в размере и даёт внешнему потребителю точку входа, но восстановлением состояния внутри системы не занимается.

Надгробий система не пишет. `encodeMessage` всегда сериализует тело сообщения, пустого значения он отправить не умеет, поэтому ключ из компактируемого топика убрать нечем: снятый с объекта прибор останется в `device.state.v1` навсегда, срока хранения у компактируемого топика нет. На стенде состав приборов не меняется, и цена этого ограничения нулевая; в системе с оборотом оборудования удаление ключа надгробием пришлось бы делать до первого снятия прибора. Как надгробие ведёт себя у брокера, показывает опыт про компакцию в [записной книжке по Kafka](kafka-notebook.md).

Автосоздание топиков выключено. Опечатка в имени переменной окружения здесь молча создала бы топик с одной партицией и тихо сломала всю модель партиционирования.

Сырой топик сжимается gzip на стороне брокера по настройке топика. LZ4 был бы быстрее, но kafkajs не распаковывает его без стороннего кодека, а живые кодеки требуют нативной сборки. Потребитель падал на первой же пачке, поэтому выбрана совместимость. Создание топиков при старте стека сверяет настройки и у существующих топиков, так что правка манифеста доезжает до живого стенда без пересоздания тома.

### Семантика доставки

**At-least-once с идемпотентными эффектами. Транзакции Kafka не используются.**

Гарантия «ровно один раз» через транзакции брокера закрывает связку «прочитал, обработал, записал», когда и вход, и выход это топики. Здесь выход это Postgres, транзакция брокера его не покрывает, значит ключ идемпотентности в таблице нужен в любом случае. Раз он всё равно нужен, транзакции добавляют координатора и заметно более сложное восстановление, ничего не убирая. Хуже того, неверно выведенный идентификатор транзакции ломает защиту от зависших писателей и даёт **ложное** ощущение точной доставки, что опаснее честного повтора.

Продюсер идемпотентный, с подтверждением от всех реплик. Идемпотентность продюсера снимает дубли от собственных повторов и, что важнее, сохраняет порядок внутри партиции при включённых повторах.

Консьюмер работает с ручным коммитом. Порядок строго такой:

```
пачка от брокера, разбор всех сообщений
  -> BEGIN
  -> INSERT показаний, событий и строк очереди недоставленных ... ON CONFLICT DO NOTHING
  -> COMMIT
  -> отправка ядовитых сообщений в очередь недоставленных, публикация показаний
  -> подтвердить смещения
```

Падение между записью в базу и коммитом смещения даёт повтор, а повтор не даёт эффекта. Публикация в `telemetry.readings.v1` при повторе может дать дубль, и это допустимо: топик служит живым распределением, а не хранилищем.

Состояние фильтра скачков тоже меняется только после успешной записи. Разбор пачки работает с копией, поэтому повторно доставленная пачка даёт ровно те же значения, что и в первый раз.

Размер пачки при этом ничем не настраивается: `maxBytes`, `maxBytesPerPartition`, `minBytes` и `maxWaitTimeInMs` боевой потребитель (`packages/kafka/src/consumer.ts`) не задаёт и живёт на умолчаниях kafkajs. Нарочно их выставляет только опыт про отставание в `tools/kafka-lab`, которому нужна заведомо мелкая пачка. На потоке стенда, единицы сообщений в секунду, выбирать тут нечего: пачка приходит по таймауту ожидания, а не по набранному объёму. Под настоящей нагрузкой это первое, что пришлось бы подобрать, потому что именно эти четыре числа решают, чем система платит за пропускную способность, задержкой или памятью.

**Идемпотентность обеспечена схемой базы, а не логикой приложения:**

| Эффект                  | Ключ идемпотентности                                                        |
| ----------------------- | --------------------------------------------------------------------------- |
| `ts.readings`           | `UNIQUE (device_id, metric_key, ts)`                                        |
| `ts.poll_cycles`        | `UNIQUE (device_id, ts)`                                                    |
| `core.dlq_message`      | `UNIQUE (source_topic, partition, offset)`                                  |
| `core.alarm_events`     | `UNIQUE (dedupe_key)`                                                       |
| `core.device_events`    | `UNIQUE (device_id, kind, occurred_at)`                                     |
| `core.applied_commands` | `PRIMARY KEY (command_id)`, команда исполняется только если вставка удалась |
| `core.outbox`           | `UNIQUE (aggregate_id, revision)`                                           |

Порядок гарантируется только внутри партиции, то есть внутри прибора, и этого домену достаточно: два чтения одного датчика никогда не приедут наоборот, поэтому снятие аларма не может обогнать его подъём.

### Отказы

**Классификация ошибки первична, она определяет всё поведение.**

_Транзиентная_ (база недоступна, обрыв соединения): смещение не коммитится, партиция ставится на паузу, задержка растёт экспоненциально, затем работа возобновляется. Если не выправилось, процесс честно завершается с ненулевым кодом и перезапускается.

Задержки 0.2, 0.5, 1, 2.5 и 5 секунд с джиттером, после пятой неудачи процесс завершается, и его поднимает Docker. В kafkajs позиция чтения идёт от последнего подтверждённого внутри пачки смещения, поэтому пауза партиции без подтверждения возвращает ту же пачку целиком, отдельный буфер повторов не нужен.

Вторая тонкость той же библиотеки: при ручном коммите `commitOffsetsIfNecessary()` без аргументов не делает ничего, коммитить приходится явными смещениями, причём следующими за последним прочитанным. Ошибку поймал интеграционный тест на повтор после сброса смещений. Идемпотентная база её не показывала: процессор после каждого перезапуска молча перечитывал весь сырой топик.

Транзиентные ошибки в очередь недоставленных не уходят: при десятиминутной недоступности базы она набилась бы валидными данными, которые потом никто не разберёт.

_Терминальная_ (не проходит валидацию, неизвестный профиль, кадр не той длины): повторов нет вообще. Сырые байты уезжают в отдельный топик с исходным ключом и полным набором диагностических заголовков, смещение коммитится, поток идёт дальше. Одна битая запись не останавливает партицию.

В очередь недоставленных кладутся **именно сырые байты**, без попытки разбора. Иначе сообщение, которое невозможно разобрать, физически нельзя было бы туда положить. Заголовки `x-dlq-*` несут исходные топик, партицию, смещение и время, класс ошибки, её текст, номер попытки, группу потребителя и момент первой неудачи. Та же запись в той же транзакции, что и показания, ложится в `core.dlq_message`, чтобы разбирать ядовитые сообщения запросом, а не чтением топика.

Повторная подача запускается вручную: инженер ставит запрос, шлюз кладёт его в `core.dlq_redrive`, а выполняет процессор. Шлюзу для этого понадобились бы право писать в сырой топик и роль, меняющая `core.dlq_message`, а у процессора всё это уже есть вместе с продюсером и транзакционной обвязкой. Это единственное исключение из правила одного писателя, и оно записано в манифесте полем `redriver`: процессор возвращает в сырой топик только исходные байты с исходным ключом и заголовками, новых данных от его имени там не появляется. Строки отбираются под `FOR UPDATE SKIP LOCKED`, поэтому два экземпляра не подадут одно сообщение дважды, а отметка о разборе ставится только после подтверждения брокера. Забор запроса, отбор, отправка и отметки идут одной транзакцией: процесс, убитый посреди работы, откатывает запрос обратно в очередь, и его подхватит следующий такт любого экземпляра. Состояние «в работе» поэтому снаружи не видно, до итога запрос выглядит ждущим, зато навсегда в работе он не повиснет.

Сбой между отправкой и коммитом (обрыв базы на отметках или на `COMMIT`, пачка, принятая брокером частично) даёт дубль в сыром топике, и идемпотентность показаний защищает от него не всё. Показания кадра, который теперь разбирается, лягут в базу второй раз без последствий. Ядовитый кадр упадёт снова уже с новым смещением, и `UNIQUE (source_topic, partition, offset)` новую строку очереди не поймает, а исходная после отката так и ждёт: без защиты на кадр стало бы две ждущих строки, и каждый такой сбой удваивал бы цепочку. Поэтому копия несёт заголовок `x-dlq-redrive-of` с номером исходной строки. Процессор в транзакции разбора копии закрывает эту строку, чем бы разбор ни кончился, а упавшая копия записывает номер в колонку `redrive_of` под уникальным индексом. Строку, которую прямо сейчас держит транзакция подачи, процессор пропускает через `SKIP LOCKED` и не ждёт конца её отправки, иначе пачка партиции висела бы без heartbeat: такую строку закроет сама подача, а после отката следующая копия. Если база лежала, запрос откатился в ожидание и следующий такт подал ту же строку ещё раз, до процессора дойдут две копии, но строка очереди от них появится одна. В сам топик недоставленных такая копия ляжет дважды: он остаётся журналом, а разбирается очередь по таблице. Метрика `fieldstream_processor_dlq_total` считает отправленное в этот топик, поэтому тоже учтёт копию второй неудачей. Неточным остаётся сам запрос: он завершится `failed` с нулевыми счётами, хотя часть сообщений уже ушла в топик, а их строки закроются, когда копии дойдут до процессора.

Счёт попыток едет вместе с сообщением в заголовках `x-dlq-attempt` и `x-dlq-first-failed-at`, так что новая неудача продолжает его, а не начинает заново. Заголовки проверяются строго: попытка только целым до тысячи, момент только полной меткой ISO 8601, иначе заголовок считается отсутствующим. `Date.parse` принимает и `'2026'`, а база на такой строке уронила бы транзакцию, и кривой заголовок остановил бы партицию, от чего очередь недоставленных как раз защищает. На третьей неудаче сообщение больше не подаётся и помечается окончательно отвергнутым: кадр, который не разбирает никакой декодер, иначе ходил бы по кругу, а счёт ждущих разбора на экране не опускался бы до нуля. Ключ сохраняется, поэтому murmur2 возвращает кадр в ту же партицию, откуда он ушёл.

Возвращённый кадр старше всего, что процессор уже видел по прибору: он пролежал в очереди, пока синхронизировали топологию или выкатывали профиль. Поэтому кадр с `x-dlq-attempt` только дописывает показания в базу, где они идемпотентны, а фильтры скачков, режим и двери в памяти, события прибора, алармы и живой канал не трогает. Иначе кадр часовой давности откатил бы режим прибора, поднял или снял аларм задним числом и показался бы на экране свежим значением.

Заголовкам `x-dlq-*` во входящем кадре процессор верит: по манифесту в сырой топик пишут только сборщик и сам процессор, и граница доверия проходит по праву записи в топик. Кадр с поддельным `x-dlq-attempt` обойдёт события, алармы и живой канал так же, как настоящая копия. Номер из `x-dlq-redrive-of` при этом сверяется с топиком и ключом строки очереди: кадр с чужим номером чужую строку не закроет и не займёт её место в `redrive_of`.

Отложенных повторов через топики с задержкой здесь нет: они дают больше отладки гонок, чем пользы.

При остановке процесса обязателен явный выход из группы: `beforeApplicationShutdown` отключает потребителя, и без этого группа ждала бы истечения таймаута сессии перед перераспределением, а отставание взлетело бы на тридцать секунд на ровном месте. Текущую пачку при этом никто не прерывает: обработчик пачки досчитывается до конца, а `stop_grace_period: 30s` в compose даёт ему на это время. Отдельного ожидания незавершённой пачки и досрочного подтверждения смещений в коде нет: повтор пачки после отката безвреден, а идемпотентность записи делает его невидимым.

Ребаланс здесь всегда «стоп-мир»: кооперативного протокола kafkajs не поддерживает, назначение приходит экземпляру целиком, и при входе соседа обработка встаёт у всех участников группы, а не только у тех, чьи партиции переезжают. События об отзыве партиций у библиотеки тоже нет, поэтому потерянные партиции считаются сравнением прошлого назначения с новым. Под это написан весь переезд состояния: экземпляр не дополняет прежнюю раскладку, а принимает новую и поднимает состояние своих приборов из Postgres. Замеренные паузы и раскладки лежат в опыте про ребаланс в [записной книжке по Kafka](kafka-notebook.md).

### Отставание консьюмера

Считается как разница между концом лога и подтверждённым смещением, отдаётся метрикой и через API. Рядом всегда показывается отставание **в секундах**, потому что в сообщениях оно ни о чём не говорит: тысяча сообщений это много или мало в зависимости от темпа. В секунды отставание переводится через темп подачи в топик, а не через темп разбора: это ответ на вопрос, сколько потока накоплено.

Партиция без подтверждённого смещения получает не ноль, а пустое значение, и в сумму не идёт: остановленный потребитель даёт не растущее число, а исчезнувшую из списка группу, и тревога нужна именно на пропажу группы.

Экран Конвейер показывает отставание по каждой партиции отдельно, историю суммарного отставания за последние пять минут (не больше 150 точек) и словесный тренд по трём последним точкам. Этого хватает на две характерные картины из трёх. Равномерный рост по всем партициям читается как нехватка потребителей, и потолок здесь это число партиций. Рост на одной партиции читается как перекос ключа или застрявший экземпляр, и лечится он разбором конкретного ключа, а не масштабированием. Третью картину, пилу от редких коммитов, экран не различает: коммиты в снимок не попадают, и пила на нём выглядит ровным ростом. Отдельной детекции для неё не сделано.

Как отставание ведёт себя под ровной подачей, под вбросом и без потребителя вовсе, показано числами в [записной книжке по Kafka](kafka-notebook.md).

### Эволюция схем

Реестра схем нет. Единственный источник истины это схемы `zod` в общем пакете контрактов.

Типы TypeScript выводятся из тех же схем, поэтому ни один сервис не описывает чужую структуру заново, и фронтенд использует ровно те же определения, что бэкенд. Мажорная версия входит в имя топика, версия и тип схемы едут в заголовках сообщения.

Проверяются схемой тело сообщения и его конверт, но не заголовки. Видно это на `x-trace-id`: телеметрия и циклы опроса кладут туда настоящий идентификатор трассы кадра, а состояние прибора код прибора, то есть строку вроде `RC-101`, которая под `traceIdSchema` (не короче восьми символов) не прошла бы. Сообщения это не ломает, но сквозная трасса по цепочке «кадр, показание, состояние» на этом месте рвётся. Держать заголовки схемой означало бы разбирать их на каждом сообщении, и это не сделано сознательно.

Совместимость стережёт тест, а не сервис: в тесте манифеста объявлен образец сообщения на каждый топик, типизированный схемой своего топика, поэтому новый топик без образца не соберётся, а ломающее изменение формы схемы падает здесь же. Отдельных файлов со старыми версиями в репозитории нет: образцы типизированы текущими схемами, и тест ловит не всякое ломающее изменение, а то, которое меняет форму сообщения на уже объявленной версии. Новая версия заводится решением автора, а не падением сборки.

Реестр схем с бинарным форматом был бы правильным выбором при появлении потребителя не на TypeScript или при требовании компактности. Пока таких нет, это второй контейнер и заметное усложнение сборки ради нуля пользы.

### Переигрывание истории

Три разные вещи, которые постоянно смешивают, здесь разведены явно:

1. **Догрузка событий в браузере.** Соединение оборвалось на сорок секунд, при восстановлении клиент присылает последний полученный идентификатор, сервер добивает пропущенное. К Kafka отношения не имеет.
2. **Просмотр истории.** Обычный запрос к гипертаблице за прошлое окно. Тоже не Kafka.
3. **Перепрогон из Kafka.** Сырые кадры выбранного окна заново проходят разбор и движок алармов, но с изменёнными уставками. В интерфейсе это экран Перепрогон.

Правятся при перепрогоне только уставки алармов. Показания от уставок не зависят, поэтому перепрогон не пишет ни одной строки показаний и сравнивает не показания, а эпизоды алармов. Прогон исправленным декодером не сделан: он менял бы сами показания.

**Запрос.** Инженер ставит прогон через шлюз (`POST /api/replay-runs`, право `replay.run`): окно, до 24 приборов и до 20 правок. Правка это ключ `(метрика, режим)` и только меняющиеся поля: границы, гистерезис, выдержка, признак включения; `null` снимает границу, пропущенное поле оставляет как было. Шлюз накладывает правку на уставки выбранных приборов и кладёт в `core.replay_run` оба снимка, `rules_baseline` и `rules_patched`. Правка, которая не нашла ни одной уставки, ничего не меняет или делает уставку неверной, получает 400 с текстом, где названы метрика и режим правки, а у неверной уставки ещё и прибор. Как и запрос повторной подачи, запрос живёт в таблице, а не в топике. Снимок в строке делает прогон воспроизводимым: процессор разбирает уставки оттуда общей схемой контрактов и не перечитывает живую таблицу, даже если уставки поправили сразу после постановки.

**Один прогон на стенд.** Частичный уникальный индекс по `status IN ('queued', 'running')` пропускает только один активный прогон, второй запрос получает 409. Процессор забирает строку под `FOR UPDATE SKIP LOCKED` и фиксирует захват сразу: прогон длинный и в одну транзакцию, как повторная подача, не влезает. При двух экземплярах процессора прогон исполняет ровно один.

**Окно в смещениях.** Начало и конец окна переводятся в смещения через `admin.fetchTopicOffsetsByTimestamp`, причём конец берётся с запасом в пять минут. Время сообщения это момент отправки, а сборщик после недоступности брокера досылает кадры из буфера позже, и без запаса хвост окна терялся бы. Кадры окна, досланные позже пяти минут после его конца, в прогон всё равно не попадут. Для момента, после которого сообщений нет, kafkajs 2.2.4 возвращает не `-1`, а конец лога; расчёт окна принимает оба ответа за конец лога и не пускает начало раньше первого живого смещения. Сумма разниц по партициям это объём прогона, по нему идёт полоса хода на экране. Если объём нулевой, прогон сразу завершается, не создавая группы.

**Чтение.** Имя группы `fs-replay-<id>` записывается в строку до вступления. Ручного назначения партиций у потребителя kafkajs нет, поэтому группа обычная: на событии вступления каждая недочитанная партиция переводится `seek` на свою позицию окна, а дочитанная встаёт на паузу. Смещения не подтверждаются вовсе, группа временная. Сообщение учитывается, только если его смещение не меньше текущей позиции партиции и меньше конца окна: повтор после ребаланса не считается дважды, лишнее за концом окна отбрасывается. Партиция готова, когда обработано смещение `end - 1`. Сообщение дальше позиции недочитанной партиции значит, что часть окна уже удалена по сроку хранения: позиция переносится на него, но не дальше конца окна, а число потерянных смещений уходит в журнал. Поэтому, если хвост окна удалён, партицию закрывает первое же сообщение за концом. Сбой потребителя проваливает прогон без перезапуска.

**Кадры.** Внутри окна по смещениям кадры ещё раз отбираются по времени самого кадра, `[from, to)`, и по выбранным приборам. Копии повторной подачи из очереди недоставленных пропускаются: живой поток пишет из них только показания и в движок алармов не пускает, а здесь кадр учитывался бы дважды. Кадр прибора со временем не позже последнего принятого по этому прибору считается отвергнутым: иначе снятие аларма могло бы оказаться раньше подъёма. Неразобранный кадр выбранного прибора (по ключу сообщения) тоже считается отвергнутым, но в очередь недоставленных при перепрогоне ничего не уходит.

**Два варианта.** Принятый кадр один раз проходит `processFrame` с фильтром скачков и дважды движок алармов `evaluateFrameAlarms`: с уставками «было» и «стало». Время движку приходит из кадра, системные часы в расчёте не участвуют, поэтому выдержка в циклах и гистерезис отрабатывают так же, как вживую, с какой бы скоростью ни шло чтение. Оба варианта начинают с пустой памяти алармов, и сравнение не зависит от живой базы: стоял ли процессор посреди окна, правили ли уставки, был ли открыт эпизод до начала окна. Подъём открывает эпизод варианта, снятие закрывает, открытые к концу окна остаются без снятия. Покрытие прогона это время первого и последнего принятого кадра.

**Пульс.** Раз в `REPLAY_HEARTBEAT_MS` процессор пишет ход и пульс с условием «прогон в работе и исполнитель это я». Ноль обновлённых строк значит, что прогон уже не его, и работа останавливается без записи итога. Прогон с пульсом старше `REPLAY_STALE_MS` завершает с ошибкой любой свободный экземпляр с включённым перепрогоном и заодно удаляет временные группы брошенных прогонов, кроме группы активного; группу с живым участником брокер не удалит. Срок протухания обязан вмещать хотя бы три пульса, иначе процессор не стартует. Прогон дольше `REPLAY_MAX_MS` завершается с ошибкой: это страховка от чтения, которое встало или идёт слишком долго для такого окна. Остановка процессора прерывает идущий прогон и сразу пишет ошибку, не дожидаясь брокера.

**Очередь без исполнителя.** Если процессор не запущен или перепрогон у него выключен, прогон так и висел бы в `queued` и занимал бы стенд навсегда. Поэтому ждущий дольше `REPLAY_QUEUE_TIMEOUT_MS` прогон снимает с ошибкой шлюз, перед постановкой нового и при чтении списка. Порог считается по часам базы, как и `created_at`: при спешащих часах шлюза иначе снимался бы только что поставленный прогон. Для этого у `fs_api` есть колоночное право на `status`, `error` и `finished_at`, а запрос трогает только ждущие прогоны.

**Итог.** Одна транзакция в строгом порядке. Первым идёт `finishReplayRun`: он переводит строку в `done` и блокирует её, а если строка уже не своя, транзакция откатывается без записи. Затем эпизоды обоих вариантов одной пачкой, тоже только для своего прогона и с `ON CONFLICT DO NOTHING`, и чистка: хранятся 20 последних завершённых прогонов (`done` и `failed`), более старые удаляются вместе со своими эпизодами каскадом. При сбое сначала откат, потом `failReplayRun` на чистом соединении, иначе провал откатился бы вместе с итогом. После итога потребитель останавливается и отключается, а временная группа удаляется `admin.deleteGroups` с несколькими попытками: брокер удаляет только пустую группу, а участник выходит из неё не мгновенно. Не удалённую пустую группу брокер со временем уберёт сам.

**Боевая группа не страдает.** Смещения и раскладка партиций принадлежат группе, а `fs-processor` и `fs-replay-<id>` это разные группы: вступление временной не вызывает ребаланса у боевой, `seek` и пауза действуют только внутри временной, а подтверждать ей нечего. Чтение кадры из топика не забирает. Цена в другом: перепрогон идёт в том же процессе, что и живой поток, и делит с ним цикл событий Node и пул соединений с базой.

**Предел эпизодов.** В памяти процессора каждый вариант держит не больше 20 000 эпизодов, дальше прогон завершается с ошибкой, которая просит сузить окно, взять меньше приборов или смягчить правку, а не съедает память. График одной строки получает не больше 2000 эпизодов на вариант с признаком обрезки.

**Разница.** Эпизоды двух вариантов сопоставляются по `(прибор, метрика, режим)` и пересечению интервалов, открытый эпизод тянется до конца окна. «Новые» это эпизоды «стало» без пары, «пропали» это эпизоды «было» без пары. Колонка «Вживую» считает эпизоды из `core.alarm_events` за фактическое покрытие прогона, а не за запрошенное окно, и она только справочная: живой поток мог стоять, а уставки могли меняться посреди окна.

**Боевая история не переписывается никогда.** Результат лежит в обычных таблицах `core.replay_run` и `core.replay_alarm_episode`, а `ts.readings` и `core.alarm_events` перепрогон не трогает. Сжатые чанки не предназначены для массового переписывания, а лента алармов, переписанная задним числом, перестала бы быть журналом того, что система видела на самом деле. Кнопки «применить правку» нет: уставка меняется обычной правкой на экране прибора, с текущего момента и с записью в журнал правок.

**Ограничение стенда.** Засев пишет неделю истории прямо в базу, в Kafka её нет. Перепрогнать можно только кадры, которые стенд собрал сам, и не старше срока хранения сырого топика. Предел окна берётся из манифеста топиков, а не литералом, поэтому окно и топик не разойдутся.

### Когда Kafka здесь была бы лишней

При 24 приборах и потоке примерно 5.6 сообщения в секунду (расчёт в разделе про сборщик, сырых кадров из них 2.4) Kafka избыточна **по нагрузке**. Оправдана она **по свойствам**:

1. **Развязка жёсткого такта опроса и медленного потребителя.** Опрос линии идёт с фиксированной каденцией. Если запись в базу тормозит, это не имеет права растягивать обход линии. Kafka здесь буфер с диском.
2. **Один вход, несколько независимых потребителей.** Запись истории (важна пропускная способность), движок алармов (важны порядок и свежесть), живая отдача в браузер (старые сообщения вредны). Это независимые группы над одним логом, каждая со своим смещением.
3. **Переигрывание.** В сыром топике лежат кадры как они пришли с линии, поэтому неделю можно заново прогнать через другой код. Сейчас так проверяется правка уставок алармов (экран Перепрогон), прогон исправленным декодером не сделан. Очередь такого не позволяет: сообщение прочитано и его больше нет.
4. **Топология.** Сборщик стоит в сети площадки и входящих соединений не принимает, поэтому команды приходят ему топиком, а не запросом.

Если бы нужен был только буфер, хватило бы `LISTEN/NOTIFY` в Postgres или Redis Streams. Если бы нужны были несколько потребителей без переигрывания, разумнее был бы NATS JetStream, и стек стал бы легче на гигабайт памяти. Kafka оправдана именно сочетанием всех четырёх свойств.

Поведение брокера проверяется прогонами на живом стенде: опыты лежат в `tools/kafka-lab`, их разбор в [записной книжке по Kafka](kafka-notebook.md). Разобраны порядок и ключ партиционирования, независимые группы, ребаланс, коммиты, идемпотентный продюсер, очередь недоставленных, отставание и компакция. Опыты идут на учебных топиках с префиксом `fieldstream.lab.`, боевые топики они только читают, а за собой убирают и топики, и группы. Запуск одного опыта: `pnpm --filter @fieldstream/kafka-lab run lab order`.

## Модель данных

Одна база, две прикладные схемы и три роли с минимальными правами. Отдельные базы на сервис не заводятся: расширение TimescaleDB ставится на базу, три базы означают три установки расширения и лишний вес, а изоляция достигается правами.

### Роли

```sql
fs_migrator  -- владелец схем, только миграции
fs_ingest    -- stream-processor, вставка телеметрии
fs_api       -- api-gateway, чтение
```

У роли `fs_api` **нет** права вставки в `ts.readings`, и на это есть интеграционный тест, ожидающий отказа в доступе.

В перепрогон шлюз пишет только по колонкам. Прогон он ставит вставкой в `core.replay_run` одних колонок запроса и может снять с очереди незабранный прогон (`status`, `error`, `finished_at`). Ход и итог пишет `fs_ingest`, тоже только в свои колонки, а эпизоды в отдельную таблицу. Окно, приборы, правку и снимок уставок после постановки не может поменять ни шлюз, ни процессор.

Роли создаёт контейнер миграций от имени суперпользователя перед применением миграций, идемпотентно, с паролями из окружения. Скрипт инициализации образа базы для этого не годится: он выполняется только на пустом томе, и смена пароля в `.env` молча не применилась бы. Здесь она применяется при следующем запуске стека. Там же, до первой миграции, ставятся расширения `timescaledb` и `timescaledb_toolkit` и создаются сами схемы `core` и `ts` с владельцем `fs_migrator`. Миграции поэтому начинают с непустой базы и схем не заводят. Обратная сторона: полный откат до нуля схемы не удаляет, а обратное направление `0007` снимает права `ON ALL TABLES IN SCHEMA core, ts` и на отсутствующей схеме упало бы. Откат рассчитан на возврат на шаг назад, а не на разбор базы до пустого тома: тома стенда сносятся отдельно, `docker compose -f infra/compose/docker-compose.yml down -v`, а `pnpm stack:down` их оставляет.

### Гипертаблицы

```sql
CREATE TABLE ts.readings (
  ts          timestamptz      NOT NULL,
  device_id   int              NOT NULL,
  metric_key  text             NOT NULL,
  value       double precision,
  quality     smallint         NOT NULL DEFAULT 0
);
SELECT create_hypertable('ts.readings','ts', chunk_time_interval => INTERVAL '1 day');

CREATE UNIQUE INDEX readings_device_metric_ts ON ts.readings (device_id, metric_key, ts DESC);

ALTER TABLE ts.readings SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'device_id, metric_key',
  timescaledb.compress_orderby   = 'ts DESC'
);

CREATE TABLE ts.poll_cycles (
  ts            timestamptz NOT NULL,
  line_id       smallint    NOT NULL,
  device_id     int         NOT NULL,
  ok            boolean     NOT NULL,
  error_kind    text,
  duration_ms   int         NOT NULL,
  request_count smallint    NOT NULL,
  plan_mode     text        NOT NULL
);
SELECT create_hypertable('ts.poll_cycles','ts', chunk_time_interval => INTERVAL '6 hours');

CREATE UNIQUE INDEX poll_cycles_device_ts ON ts.poll_cycles (device_id, ts DESC);

ALTER TABLE ts.poll_cycles SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'line_id, device_id',
  timescaledb.compress_orderby   = 'ts DESC'
);

-- политики сжатия и хранения заводятся отдельной миграцией 0006_policies.sql:
-- сжатие с двух суток, хранение 30 суток, те же сроки у ts.poll_cycles
```

Гипертаблиц две. У показаний кусок в сутки и сегментация по прибору и метрике: по ним идут все выборки серий. У циклов опроса кусок в шесть часов и сегментация по линии и прибору, потому что запросы к ним всегда про линию за последние часы, а не про метрику за неделю. Итог каждого обращения к прибору пишется сюда даже тогда, когда прибор не ответил и кадра нет: иначе отказ был бы не виден ни на одном экране.

Уникальный индекс обязан включать колонку партиционирования, и он же служит ключом идемпотентности при вставке.

**Узкая форма таблицы выбрана осознанно.** Две модели приборов имеют разный набор метрик, широкая таблица требовала бы изменения схемы на каждую новую метрику. При одной жёсткой схеме прибора широкая таблица была бы быстрее.

Колонка `quality` объявлена четырьмя значениями (`ok`, `stale`, `substituted`, `bad`), а конвейер пишет два. `ok` это измеренное значение, `substituted` это подстановка фильтра скачков вместо отвергнутого выброса. `stale` не пишет никто: протухание решается не качеством отдельной строки, а деревом здоровья, которое смотрит на время последнего кадра прибора. `bad` встречается только на чтении, как значение по умолчанию для строки без качества. Два лишних кода оставлены в перечислении осознанно: они стоят ноль и понадобятся, как только появится второй источник показаний, где протухшее значение придётся отличать от измеренного.

**Разбиение по пространству не включено.** Выигрыш оно даёт на кластере из нескольких узлов, на одном узле это лишняя сложность без эффекта.

**Инвариант для сжатых кусков:** живая запись всегда идёт в горячий кусок, политика сжатия стоит на двух сутках, перепрогон пишет только в обычные таблицы схемы `core`, история не переписывается. Следовательно ни одна операция боевого конвейера не попадает в сжатый кусок, и вопрос о поведении вставки по сжатым данным в нём не возникает.

Исключение ровно одно, и оно вне конвейера: засев (`tools/seed`) заливает неделю истории задним числом и правит уже залитые сутки, накладывая оттайки и происшествия. Эти правки попадают в сжатые куски, а предел TimescaleDB на распаковку в одной транзакции (сто тысяч строк) заливку останавливает, поэтому засев снимает его на время своей транзакции. Разовой заливке стенда это допустимо, боевому конвейеру нет, и потому правка истории живёт в инструменте, а не в сервисе.

### Непрерывные агрегаты

Хранятся **сумма и количество, а не среднее**. Среднее от средних неверно при разном числе замеров в интервале, и без суммы с количеством верхний уровень нельзя построить корректно.

Сам агрегат сумму и количество и хранит, а вот удобные представления `ts.v_readings_1m` и `ts.v_readings_1h` отдают наружу уже среднее и количество. Запросу серии, который группирует ещё крупнее, сумма поэтому нужна обратно, и он собирает её как `sum(avg_value * n)`. Результат верный, но круг через деление и умножение в плавающей точке лишний: правильнее было бы вынести `sum_value` в представление. Колонка не добавлена, чтобы не трогать уже накатанную миграцию ради формы запроса; на глубине истории стенда разницы в числах это не даёт.

Агрегаты иерархические: часовой строится **над минутным**, а не над сырой таблицей.

Правила, которые нужно соблюдать при изменении агрегатов:

1. У каждого уровня своя политика обновления. Без неё верхний агрегат не материализуется сам.
2. Ширина интервала родителя кратна интервалу потомка.
3. Отступ от конца у родителя строго больше, чем у потомка, иначе родитель считает по недоматериализованным данным.
4. Режим реального времени на нижнем уровне обязателен, иначе последняя минута пропадает с живого графика. Включён он у всех трёх агрегатов, а не только у нижнего: верхний уровень тогда не отстаёт от нижнего на окно материализации, и переход между источниками при смене окна графика не даёт ступеньки.
5. Срок хранения сырой таблицы не залезает в окно, которое ещё обновляют политики агрегатов.

Агрегатов на самом деле три: минутный и часовой по показаниям и пятиминутный по циклам опроса (`ts.poll_cycles_5m`). Последний вместе с представлением `ts.device_timeout_hint`, которое считает рекомендуемый таймаут прибора как пять его p99, сейчас не читает ни один сервис: живой интерфейс берёт ту же рекомендацию из кольцевого окна сборщика на 2000 последних обращений, а не из базы. Агрегат тем не менее обновляется каждые пять минут, хранится 90 суток и тянет за собой расширение `timescaledb_toolkit`, без которого не накатывается миграция `0005`. Сделано это как заготовка под подсказку таймаута по всей истории, а не по одному сборщику.

Одно и то же правило при этом записано дважды: в SQL представления (`packages/db/migrations/0005_continuous_aggregates.sql`) по шестичасовому окну с порогом в сто отсчётов и в TypeScript сборщика (`services/edge-collector/src/polling/latency.ts`) по кольцу из 2000 последних обращений. Числа совпадают: пять p99, округление вверх до сотни миллисекунд, пол в 500 мс и те же сто отсчётов минимума. Пока представление никто не читает, разойтись они не могут заметно, но общего источника у них нет, и это второе место, которое придётся свести, если подсказка таймаута пойдёт из базы.

### Правило выбора источника

```
окно <= 6 часов   -> ts.readings (сырые)
окно <= 7 дней    -> минутный агрегат
иначе             -> часовой агрегат
```

Поверх всегда накладывается группировка по интервалу `окно / maxPoints`. Умолчание `maxPoints` это 2000 точек (`packages/contracts/src/series.ts`), схема запроса принимает от 10 до 5000 (`packages/contracts/src/api/read.ts`), а интерфейс просит 800: больше точек, чем пикселей по ширине графика, рисовать незачем. Шаг при этом не может стать мельче разрешения источника, поэтому на коротком окне точек приходит столько, сколько их есть. Ответ содержит сведения о том, откуда взяты данные и какой шаг, и интерфейс показывает это подписью под графиком.

Функция выбора лежит в общем пакете контрактов и доступна и серверу, и браузеру, поэтому подпись под графиком не может разойтись с тем, откуда данные пришли на самом деле.

Это закрывает сразу две типичные беды: эндпоинт без ограничения, отдающий всю историю, и интерфейс, перезапрашивающий всё окно чаще, чем данные вообще меняются.

### Миграции

Чистый SQL, каждая с прямым и обратным направлением. Применяются одноразовым контейнером до старта сервисов, а не при старте приложения, иначе две реплики процессора гонятся за одну миграцию. Перед работой берётся блокировка уровня базы.

Начиная с `0008`, новая таблица приходит вместе со своими правами в той же миграции, а права первых таблиц собраны в `0007_grants.sql`. Например, `0014_replay.sql` заводит прогоны перепрогона и их эпизоды и тут же раздаёт права шлюзу и процессору, а обратное направление удаляет обе таблицы.

Держится это правило дисциплиной, а не машиной: `ALTER DEFAULT PRIVILEGES` не используется нигде, поэтому таблица, заведённая без своего `GRANT`, просто останется недоступной сервису, и узнается это на первом запросе, а не при накате. Тестом закрыты границы прав там, где ошибка дороже всего: интерфейс не может писать в телеметрию, очередь недоставленных и таблицы перепрогона доступны ровно тем ролям, которым положено. Права на служебные таблицы вроде учётных записей, очереди исходящих и прогресса загрузки проверками не закрыты.

ORM не используется: DDL TimescaleDB ни один ORM нормально не выражает, а натягивать на него гипертаблицы, непрерывные агрегаты и политики означало бы держать половину схемы в обходных путях. Схемой владеет SQL пятнадцати миграций в `packages/db/migrations`, запросами рукописный SQL в тринадцати модулях `packages/db/src/store` поверх драйвера `pg`, типы результата описаны рядом с запросами. Цена известна: имя колонки меняется вручную во всех запросах, которые её трогают, и компилятор об этом не предупредит. Подробности в [0008](adr/0008-sql-without-orm.md).

## Фронтенд

React 19, TypeScript в строгом режиме, Vite. MUI для каркаса, SCSS-модули по БЭМ для собственных стилей, uPlot для временных рядов, TanStack Query для серверного состояния.

**uPlot вместо более привычного Chart.js** потому, что график за неделю это десятки тысяч точек: uPlot рисует их на canvas за единицы миллисекунд, а его минифицированная сборка весит 51 КБ и 22 КБ в gzip. Chart.js остался бы правильным выбором, если бы графиков было три штуки по двести точек. Подробности в [0011](adr/0011-uplot.md).

**Код в одном чанке.** Сборка кладёт весь интерфейс в один файл на 1.0 МБ (320 КБ в gzip) и печатает предупреждение Vite про чанк крупнее 500 КБ. Разбиения по маршрутам нет: приложение за авторизацией, открывают его на внутренней сети, и один запрос без водопада догрузок здесь честнее, чем шесть ленивых маршрутов ради первой отрисовки. Предел предупреждения поднимать не стали, чтобы цифра оставалась на виду.

### Состояние

Серверное состояние живёт только в TanStack Query, Redux нет. Локальное состояние на `useState`, а как только в компоненте набирается два и более связанных значения, вместо них `useReducer`. Глобального минимум, и лежит оно в двух маленьких хранилищах `zustand`: сессия вкладки с токеном доступа в памяти (`apps/web/src/shared/auth/session-store.ts`) и состояние живого канала (`apps/web/src/shared/sse/live-store.ts`). Поправка часов хранится отдельным модулем `apps/web/src/shared/time/serverClock.ts`, единственным местом во фронте, которому разрешено читать системные часы.

**Живые данные не инвалидируют кэш.** Событие точечно патчит закэшированные данные, к сети запрос не идёт. К сети идёт только при явном сигнале рассинхронизации. На это есть тест, который проверяет, что сетевого запроса не произошло.

Поток телеметрии дросселируется **на сервере** до одного обновления в секунду на прибор независимо от частоты опроса: браузер не должен получать больше, чем способен отрисовать.

### Экраны

1. **Обзор.** Дерево объектов с агрегированным статусом и машинной причиной. Плитка показывает **прочерк**, а не последнее известное число, если состояние старше порога: устаревшие данные не выдаются за измеренные.
2. **Прибор.** Живые значения, график с выбором окна и подписью источника, полоса режимов под графиком (видно, что рост температуры совпал с оттайкой), панель уставок с переключением режима, журнал изменений уставок. Отдельно карта регистров: ось адресов, параметры как блоки, склеенные блоки нарисованы скобками, переключатель режима плана меняет число запросов и фактическую длительность цикла на глазах.
3. **Алармы.** Живая лента, история с курсорной постраничной навигацией, подтверждение с оптимистичным обновлением и откатом при ошибке.
4. **Конвейер.** Схема потока от симулятора до браузера с темпом по топикам, группы потребителей с раскладкой партиций и полосой отставания на каждой партиции, история отставания, журнал ребалансов и очередь недоставленных с повторной подачей. Снимок брокера шлюз собирает сам раз в две секунды, экран его опрашивает: это снимок, а не поток событий, и досылать его после обрыва бессмысленно.
5. **Отказы.** Панель поломок по линиям и приборам и приборы защитных механизмов выбранного источника: размыкатель с отсчётом до пробы, лестница переподключения по фактическим задержкам, полоса сторожа обхода, гистограмма времени ответа с перцентилями и рекомендуемым таймаутом. Ниже сценарии стенда с запуском, ходом прогона и бейджем последнего итога.
6. **Перепрогон.** Форма с приборами (быстрый выбор всех холодильных камер), окном (15 мин, 1 ч, 6 ч, 24 ч или своё в пределах срока хранения) и правками уставок с подсказкой текущего значения, плюс кнопка-пример «Граница испарителя в оттайке +8». Ход прогона с полосой по смещениям сырого топика и именем временной группы, таблица «Было, Стало, Новые, Пропали, Вживую» и график выбранной строки: кривая параметра, полосы эпизодов обоих вариантов и линии порогов до и после правки. Без права `replay.run` форма только для чтения.

Права решают, какие вкладки видны: `apps/web/src/app/AppLayout.tsx` скрывает недоступные. Маршрутизатор при этом о правах не знает, поэтому прямой заход по адресу вкладки, которой нет в правах, отрисует экран и покажет «Нет доступа» уже по ответу 403 от шлюза. Это осознанно: последнее слово о правах всё равно за сервером, а вторая проверка в браузере добавила бы место, где две копии правил расходятся.

### Состояния, адаптивность и доступность

У каждого экрана есть состояния: загрузка (скелетоны фиксированной высоты, а не спиннер на всю страницу), пусто, ошибка (с различением «сервер недоступен» и «сессия отозвана»), устаревшие данные, недоступность живого канала.

Адаптивность держится на четырёх контрольных ширинах: 480, 640, 900 и 1100 пикселей, шестнадцать медиазапросов в SCSS-модулях. Широкие таблицы и схемы лежат в контейнере с горизонтальной прокруткой и собственной минимальной шириной (лента алармов 1060 пикселей, схема конвейера 1080), поэтому на узком экране они прокручиваются вбок, а не сжимаются в нечитаемое. У панелей инструментов размеры фиксированы, чтобы кнопки не переставлялись при смене данных.

Доступность: роли и подписи расставлены руками, новые события объявляются через `aria-live`, прокручиваемые области получают фокус (`tabIndex`) и листаются стрелками средствами браузера. Единственное модальное окно приложения это подтверждение запуска сценария, и ловушку фокуса в нём даёт `Dialog` из MUI, а не свой код. Нарушения ловит axe в сценариях Playwright.

Чего здесь нет. Своей навигации по строкам таблицы с клавиатуры нет: стрелки листают контейнер, а не переводят выделение по строкам. Раскладку на узких экранах не проверяет ни один автоматический прогон: у Playwright единственное окно 1440x900, размер окна ни один сценарий не меняет, а юнит-тесты идут в jsdom, который о раскладке не знает. Проверки axe идут в тёмной теме, принятой по умолчанию, и только на экранах без открытого модального окна.

### Построитель плана чтения

От плана чтения зависят число запросов к прибору и длительность цикла опроса, поэтому он разобран отдельно.

План превращает описание прибора в минимальный набор запросов. Соседние адреса одного типа регистров склеиваются в блочное чтение по правилу **«только вплотную»**: разрыв даже в один регистр рвёт блок. Поэтому автоматически собранный блок **никогда не читает регистр, который не нужен ни одному параметру**.

Учитываются предел в 125 регистров на запрос (ограничение протокола), явно объявленные блоки, требование, чтобы параметр помещался в блок целиком (32-битная величина не может быть разорвана между запросами), запрет перекрытий и запрет блоков, не покрывающих ни одного параметра.

На реальных профилях это даёт **3 запроса вместо 9** на счётчике и **4 вместо 9** на контроллере. Есть и режим «по запросу на параметр», нужный для наглядного сравнения.

Ключевой тест здесь не на числа, а на инвариант: **значения, прочитанные по склеенному плану, побайтово совпадают со значениями, прочитанными по наивному**.

### Границы зависимостей

Проверяются в трёх местах:

1. **Компилятор.** Ссылки между проектами перечисляют только разрешённые пакеты, поле `exports` без подстановок закрывает глубокие импорты во внутренности чужого пакета.
2. **Линтер.** Зоны запрещённых импортов: в контрактах нельзя ничего серверного, потому что пакет обязан собираться в браузерный бандл; в доменной логике нельзя базу и брокер.
3. **Тест.** Проверка направления зависимостей запускается и обычным тестом, и шагом CI, поэтому падает так же громко, как упавшая бизнес-логика, и её нельзя заглушить построчным отключением правила.

Проверка идёт по `packages`, `services` и `apps`. Каталог `tools` под неё не попадает намеренно: инструменты (`arch-check`, `topic-matrix`, `seed`, `scenario-ci`, `kafka-lab`, `bench`) в образы не уезжают, работают против уже поднятого стенда и ходят в сеть по делу, поэтому те же запреты им только мешали бы. Типы и линтер их при этом проверяют наравне со всеми.

## Docker

Цель: `git clone`, копирование файла окружения, одна команда, и система работает с непустыми графиками без единого ручного шага.

Порядок старта задан условиями готовности:

```
timescaledb (готова)                  -> миграции (завершились)
kafka (готова)                        -> создание топиков (завершилось)
миграции                              -> засев истории
миграции + создание топиков           -> stream-processor, api-gateway
api-gateway (жив)                     -> web
device-sim (готов) + создание топиков -> edge-collector
```

Симулятор ни от кого не зависит и поднимается сразу вместе с базой и брокером: ему нечего ждать, приборы стенда живут в нём самом. Процессор и шлюз ждут одного и того же и стартуют параллельно, а не друг за другом. Одна оговорка про веб: он ждёт от шлюза живого процесса, а не готовности к базе, потому что HEALTHCHECK образа опрашивает `/health/live`. Так сделано нарочно: пока база и брокер поднимаются, страница уже должна открываться и показывать панель готовности, а не ошибку прокси.

Что происходит в первые полторы минуты после подъёма стенда. Секунды ниже это наблюдение при одном подъёме на обычной рабочей машине с прогретыми образами, а не замер: подъём стенда `pnpm bench` не снимает, и на другом железе порядок стадий сохранится, а времена сдвинутся.

| Время   | Что происходит                                                                                       |
| ------- | ---------------------------------------------------------------------------------------------------- |
| 0-15 с  | поднимаются брокер и база, создаются топики, катятся миграции                                        |
| 12 с    | страница уже открывается и показывает панель готовности со стадиями, а не пустой экран и не ошибку   |
| 15-45 с | засевается неделя истории в минутном разрешении                                                      |
| 20 с    | стартует сборщик, дерево здоровья появляется целиком в состоянии `startup_grace` с обратным отсчётом |
| 45 с    | графики рисуются по засеянной истории                                                                |
| 90 с    | окно ожидания истекает, дерево зеленеет, идут настоящие события                                      |

В историю заранее засеяны три происшествия: RC-103 сорок пять минут держит температуру подачи выше уставки (`warning`), RC-107 двадцать минут идёт с перегревом выше 16 K (`critical`), PM-203 двенадцать минут просаживает напряжение второй фазы ниже 207 В (`warning`). Заданы они руками, а не случайно, поэтому одинаковы на каждом стенде. Без готовых происшествий список алармов и навигация по истории пусты и бессмысленны в первую минуту.

Ни один сервис не уходит в цикл перезапуска при недоступной Kafka: сервисы повторяют попытки с возрастающей задержкой и честно сообщают, что ещё не готовы.

Образ собирается многостадийно: слой зависимостей отделён от слоя кода, поэтому правка одной строки не пересобирает зависимости. Итоговый образ содержит только рабочие зависимости, без инструментов сборки. Контейнеры работают не от суперпользователя. Проверка живости у сервисов сделана скриптом на Node, а не через `curl`, которого в минимальном образе нет; у веб-образа это `wget` из базового образа nginx, который дёргает `/healthz` самого входа, не дожидаясь шлюза.

Ни одного значения по умолчанию для секретов: отсутствие обязательной переменной окружения это падение на старте с внятным списком, а не тихая работа с известным всем значением.

## Тестирование

Тестируется то, где ошибка стоит дорого и где логика нетривиальна.

### Чистые функции

Быстрые, без базы и брокера, и именно они ловят регрессии в содержательной части.

- **Построитель плана чтения.** Табличные случаи: склейка только вплотную, разрыв рвёт блок, предел в 125 регистров, параметр не помещается в блок целиком, перекрытие объявленных блоков, регистры разных типов не склеиваются. Плюс порождающий тест со случайными профилями, проверяющий инварианты: каждый параметр покрыт ровно одним блоком, блоки не пересекаются, при нулевом допустимом разрыве не читается ни одного лишнего регистра, а значения по склеенному плану совпадают со значениями по наивному.
- **Кодек.** Кодирование и декодирование по всем сочетаниям типа и порядка байтов, отрицательные значения, обратный порядок слов у счётчика, множители и точность, битовые маски, перечисления.
- **Алармы.** Гистерезис (не дребезжит ровно на границе), выдержка, смена режима меняет применимую уставку, заглушенные режимы, снятие аларма при удалении уставки, отсутствие значения не влияет на счётчик.
- **Дерево здоровья** как автомат: все машинные причины, окно после старта, асимметрия агрегации у шлюза отдельным именованным тестом.
- **Размыкатель и задержки:** два отказа уводят источник на пробу, успех сбрасывает, джиттер не вырожденный и укладывается в границы, жёсткий таймаут срабатывает на промисе, который никогда не завершается.
- **Перепрогон.** Ядро на голых объектах: граница 8 в оттайке даёт эпизод, а 12 нет, кадры вне окна и чужих приборов не участвуют, кадр не по порядку отвергается, предел эпизодов даёт понятную ошибку. Окно по смещениям: конец лога вместо `-1`, повторы и сообщения за концом окна не учитываются, удалённые по сроку хранения смещения пропускаются, но не дальше конца окна. В шлюзе наложение правок и строки разницы.

Все переходы состояний проверяются **без реального ожидания**: время инжектируется.

### Контрактные

Тест манифеста держит по образцу сообщения на каждый топик, типизированному схемой своего топика: новый топик без образца не собирается, семь образцов тест дополнительно прогоняет через `safeParse`, и рядом проверяет, что подделанный снимок линии схему не проходит. Сверяются там же имена, ключи, число партиций и права записи; схемы алармов и здоровья разобраны отдельными тестами сообщений. Чистоту контрактов держит не тест, а линтер: в `packages/contracts` запрещены импорты `kafkajs`, `pg`, `react`, `@nestjs/*` и `node:*`, а правило `contracts-are-leaf` в `.dependency-cruiser.cjs` не пускает в них ни один пакет монорепы. Направление зависимостей между пакетами проверяет обычный тест `tools/arch-check`.

### Интеграционные

На настоящих Kafka и TimescaleDB в контейнерах, запускаются отдельной командой `pnpm test:integration`, потому что требуют Docker; лежат в `packages/db`, `services/stream-processor`, `services/api-gateway` и `tools/seed`. Вся содержательная проверка схемы базы держится на одном из них: юнит-тесты `packages/db` работают на подменённом драйвере и проверяют форму запроса и преобразование типов, а не поведение базы. Ниже не полный перечень, а утверждения, ради которых заведён этот слой:

1. Повторная доставка того же батча не меняет число строк.
2. Сброс смещений группы и повторное чтение того же батча не добавляют ни строки, а эпизод аларма, открытый до перезапуска процессора, снимается уже после него: состояние берётся из базы, а не из памяти.
3. Неразбираемое сообщение уезжает в очередь недоставленных сырыми байтами, партиция не блокируется.
4. Повторная подача возвращает сообщение в **ту же** партицию.
5. Кратковременная недоступность базы даёт паузу и полное восстановление без потерь.
6. Часовой агрегат даёт те же значения, что прямой запрос по сырой таблице.
7. Роль интерфейса не может писать в таблицу телеметрии.
8. Перепрогон с правкой границы испарителя +12 на +8 даёт срабатывание только в варианте «стало», кадры вне окна не учтены, после прогона временной группы в брокере нет, а смещения боевой группы процессора не сдвинулись.

Чего интеграционные тесты не проверяют: фоновые задания TimescaleDB. Контейнер базы в них поднимается с `timescaledb.max_background_workers=0`, иначе планировщик срабатывал бы посреди проверок и делал бы их плавающими. Значит, политики сжатия, хранения и обновления агрегатов из миграции `0006` в тестах не исполняются ни разу: проверены ручное `compress_chunk` и ручной `refresh_continuous_aggregate`, то есть то, что политика делает, но не то, что она заведена и попадает в нужное окно. Это сознательный размен устойчивости тестов на непроверенную строчку конфигурации, и живой стенд остаётся единственным местом, где эти политики видно в работе.

### Интерфейс

Веб проверяется на двух уровнях. Юнит-тесты в jsdom (`apps/web/test`) берут экраны целиком с поддельной сетью и поддельными часами: живое событие патчит кэш, не сходив в сеть; подтверждение аларма откатывается при ошибке; форма перепрогона без права `replay.run` только читается; карта регистров пересчитывает число запросов при смене режима плана. Сценарии Playwright (`apps/web/e2e`) идут против поднятого стенда, то есть вместе со шлюзом, брокером и базой, а не против разметки. Отдельный файл сценариев прогоняет axe по входу, обзору, прибору на трёх вкладках и ленте алармов и требует пустого списка нарушений.

### Сценарии стенда

Сценарии это тесты против поднятого стенда целиком. Описание в YAML вносит настоящую поломку через симулятор и ждёт наблюдаемого поведения: разомкнулся размыкатель, прибор ушёл в offline, поднялся аларм, очередь недоставленных не выросла. Исполнитель в пакете `scenarios` не знает про сеть и базу, всё внешнее приходит через порты, поэтому сам он проверяется модульными тестами на поддельных часах. Прогон исполняет шлюз и пишет ход в `core.scenario_run`, а у кнопки интерфейса и у CI путь один: CI не держит своей копии проверок, а запускает те же прогоны через API и читает их итог. Одновременно идёт один прогон, и держит это уникальный индекс базы, а не соглашение. Экземпляр шлюза, исполняющий прогон, отмечает в его строке пульс: прогон упавшего экземпляра завершает с ошибкой любой другой, а экземпляр, чей прогон завершили без него, прерывает исполнение и снимает внесённые поломки.

### Замеры

Числа про стенд снимает `pnpm bench` с поднятого стенда. Замеры закрывают темп записи, время от кадра до события живого канала, отставание групп, память и процессор контейнеров, размеры образов и томов, сжатие кусков гипертаблицы и время выборок серии. Каждая строка отчёта печатается вместе с командой, которой её повторить руками. Ключ `--load` на время прогона переводит линии на частый такт опроса и возвращает прежний такт даже при срыве замера. Как этим пользоваться, написано в [docs/STAND.md](STAND.md).

### Что сознательно не тестируется

Контроллеры с подменёнными сервисами и проверкой «подмена была вызвана»: такой тест проверяет, что код написан так, как написан. Подмена брокера в модульных тестах: она проверяет подмену, а не брокер. Снимки целых страниц. Тривиальные преобразования и конфигурация.

### Компромиссы

- Кольцевой буфер событий живёт в памяти инстанса, поэтому при нескольких инстансах нужны либо липкие сессии, либо явный сигнал рассинхронизации, который здесь и сделан.
- Сборщик при недоступном брокере отбрасывает самые старые кадры вместо роста в памяти. Это осознанная потеря данных в обмен на выживание процесса.
- Одна реплика брокера в демо-конфигурации означает, что его потеря это потеря данных.
- Перепрогон сравнивает два варианта уставок на одних и тех же кадрах, а не результат с живой базой. Живые эпизоды показаны рядом только для справки: сравнение с ними смешало бы правку с простоями процессора и прежними правками уставок.
- Перепрогон идёт в процессе `stream-processor` рядом с живым потоком: отдельный режим запуска не нужен, но цикл событий Node и пул соединений с базой у них общие. Окно при этом не длиннее срока хранения сырого топика, а сам прогон ограничен `REPLAY_MAX_MS`.

### Известные ограничения

Полный список того, что сделано не до конца или стоило бы денег при росте. Каждое ограничение названо с причиной, по которой оно оставлено. Те, что привязаны к одной подсистеме, разобраны в её разделе и здесь только перечислены со ссылкой.

Сквозные:

- Причина здоровья `polling_disabled` деревом поддержана, но живой поток её не выставляет: процессор строит вход дерева с зашитым признаком «опрос идёт», а снимок линии с полем `running` читает только шлюз, для экрана Отказы. После `line.disable` приборы через несколько минут станут `stale`, а затем `offline`, и остановленную командой линию дерево не отличит от молчащей. Оставлено как есть: чтобы причина заработала, процессору пришлось бы читать ещё один топик ради одного поля.
- Окно повтора обновления токена и защита от двойной ротации живут в памяти экземпляра шлюза (`services/api-gateway/src/auth/auth.service.ts`). Сами сессии и ведро ограничителя входов лежат в базе и общие, а вот повтор потерянного запроса, попавший на соседний экземпляр без липких сессий, будет расценен как кража токена и закроет сессию. В демо-составе шлюз один, поэтому окно не вынесено в базу.
- Просроченные сессии обновления и вёдра ограничителя входов не удаляются: у роли `fs_api` на `core.refresh_sessions` и `core.rate_limit` нет права `DELETE`, а задачи уборки нет. Отозванная сессия перестаёт действовать по дате, но строка остаётся. На стенде обе таблицы малы, в рабочей системе понадобилась бы уборка по расписанию.
- Право `users.manage` объявлено в списке модулей, но маршрута и экрана у него нет. Личные разрешения и запреты из `core.user_permissions` читаются и применяются поверх роли, а меняются правкой в базе: у роли `fs_api` на эту таблицу только чтение.
- Право `commands.send` и маршруты `POST /api/commands` и `GET /api/commands/:id` есть и работают, а экрана команд в интерфейсе нет: команда ставится запросом к API, её ход читается тем же запросом, а результат виден на экране Отказы как сменившийся такт или режим плана. Оставлено так потому, что видов команд четыре и все они меняют режим опроса, а на экране Отказы и так видно, что команда доехала.

Разобранные по месту:

- Надгробий система не пишет, поэтому ключ из компактируемого топика убрать нечем, а заголовки сообщений схемой не проверяются, и `x-trace-id` у состояния прибора несёт код прибора вместо идентификатора трассы. См. [Kafka](#kafka).
- Размер пачки боевого потребителя (`maxBytes`, `minBytes`, `maxWaitTimeInMs`) не настраивается: на потоке стенда выбирать нечего. См. [Kafka](#kafka).
- Пилообразный рост отставания от редких коммитов экран Конвейер не отличает от ровного. См. [Kafka](#kafka).
- Пятиминутный агрегат `ts.poll_cycles_5m` и представление `ts.device_timeout_hint` не читает ни один сервис, а само правило рекомендуемого таймаута записано дважды, в SQL и в TypeScript. См. [Модель данных](#модель-данных).
- Удобные представления агрегатов не отдают `sum_value`, и запрос серии восстанавливает сумму как `sum(avg_value * n)`. См. [Модель данных](#модель-данных).
- Два кода качества из четырёх (`stale` и `bad`) конвейер не пишет никогда. См. [Модель данных](#модель-данных).
- Правило «новая таблица приносит свои права» держится дисциплиной автора: `ALTER DEFAULT PRIVILEGES` не используется, и права служебных таблиц тестами не закрыты. См. [Модель данных](#модель-данных).
- Полный откат миграций не удаляет схемы `core` и `ts`: их заводит `bootstrapDatabase` до первой миграции. См. [Модель данных](#модель-данных).
- Каталог `tools` не попадает под проверку границ зависимостей. См. [Пакеты монорепы](#пакеты-монорепы).
- Политики сжатия, хранения и обновления агрегатов не исполняются ни в одном тесте: контейнер базы поднимается без фоновых рабочих. См. [Тестирование](#тестирование).
- Маршрутизатор фронтенда о правах не знает: прямой заход по адресу недоступной вкладки отрисует экран и покажет «Нет доступа» по ответу 403. См. [Фронтенд](#фронтенд).
- Раскладку на узких экранах, светлую тему и открытое модальное окно не проверяет ни один автоматический прогон, своей навигации по строкам таблицы с клавиатуры нет, а весь интерфейс собирается в один чанк на 1.0 МБ. См. [Фронтенд](#фронтенд).
