## Задача

Собирать телеметрию с промышленных приборов, которые опрашиваются по Modbus, хранить историю, считать по ней алармы и показывать всё это в реальном времени в браузере.

Задача звучит просто ровно до момента, когда выясняется, что приборы отвечают медленно, иногда не отвечают вовсе, а иногда отвечают мусором; что физическая линия связи одна на десяток приборов; что история растёт на миллионы строк в сутки и её всё равно надо показывать графиком за месяц; и что «авария» это не булево значение, а состояние, зависящее от режима работы объекта.

Система поднимается одной командой и не требует железа: приборы эмулирует отдельный сервис, говорящий по настоящему протоколу.

## Предметная область

Демо-стенд это сеть холодильного оборудования. Домен выбран потому, что даёт настоящие, а не выдуманные инженерные требования, и при этом понятен без отраслевого контекста.

### Физика

Холодильные контроллеры и счётчики электроэнергии подключены по RS-485 к Ethernet-шлюзам. Шлюз отдаёт Modbus TCP.

RS-485 это разделяемая линия. Параллельные запросы в неё физически недопустимы: два одновременных кадра сталкиваются, и приёмник получает мусор. Отсюда следует главное ограничение всей системы: **на линию приходится ровно один последовательный цикл опроса**. Из этого ограничения растут воркер на линию, три предохранителя от зависания и размыкатель на конкретный прибор.

Второе физическое ограничение это скорость. На 9600 бод кадр Modbus передаётся за десятки миллисекунд, и разница между 11 запросами и 3 запросами на прибор становится разницей между укладыванием в такт опроса и неукладыванием.

### Иерархия объектов

```
Site (SITE-A, SITE-B)
 └─ Gateway (GW-01, GW-02, адреса из 192.0.2.0/24)
     └─ Line (L1..L4, baud 9600/19200, опрос 10 с, таймаут 600 мс)
         └─ Device (slaveId 1..8)
```

Итого 24 прибора, 4 линии, 2 шлюза, 2 площадки.

### Модели приборов

Заведены ровно две, и этого достаточно, чтобы покрыть все интересные случаи кодирования.

| Профиль                             | Коды             | Что интересного                                                                   |
| ----------------------------------- | ---------------- | --------------------------------------------------------------------------------- |
| `rc-2000`, холодильный контроллер   | `RC-101..RC-112` | знаковый `int16` со `scale` 0.1, битовая маска аварий, перечисление состояний     |
| `pm-3phase`, счётчик электроэнергии | `PM-201..PM-212` | `float32` и `uint32`, разные порядки слов у разных параметров, монотонный счётчик |

Прибор описан **данными**, а не кодом: секции, параметры с адресом, типом, порядком байтов, множителем, точностью. Исполняет описание один общий движок. Добавление модели прибора это один файл и ноль правок в сервисах.

### Режимы работы и уставки

У камеры есть режимы `cooling`, `defrost`, `service` и `off`. Во время оттайки температура законно растёт на шесть и более градусов.

Если уставку хранить парой чисел на параметр, аларм по верхней границе будет срабатывать на всём складе каждые сорок минут, и его отключат в первый же день. Поэтому уставка хранится по ключу `(прибор, метрика, режим)`, а в режимах `service` и `off` алармы заглушены: холодная или обслуживаемая камера иначе выдаёт аварию по всем параметрам сразу.

Это не украшение, а требование, без которого система бесполезна.

## Схема системы

```
  +---------------------------------------------------------------+
  |                    Docker network: fieldstream                  |
  +---------------------------------------------------------------+

   [device-sim]              Modbus TCP (порты 5020..5023)
   4 TCP-сервера,      <---------------------------------+
   24 slave-адреса,                                      |
   API инъекции поломок <--- HTTP ---+                   |
                                     |          +----------------+
                                     |          | edge-collector |
                                     |          | 4 LineWorker,  |
                                     |          | размыкатель,   |
                                     |          | план чтения    |
                                     |          +----------------+
                                     |              |         ^
                                     |     сырые    |         | команды
                                     |     кадры    v         |
  +------------------------------- KAFKA (KRaft, 1 брокер) --------------+
  |                                                                      |
  |  fieldstream.telemetry.raw.v1       key=deviceCode   6p   7 суток    |
  |  fieldstream.collector.cycles.v1    key=lineCode     3p   3 суток    |
  |  fieldstream.telemetry.readings.v1  key=deviceCode   6p   24 часа    |
  |  fieldstream.device.state.v1        key=deviceCode   3p   COMPACT    |
  |  fieldstream.alarms.events.v1       key=deviceCode   3p   30 суток   |
  |  fieldstream.device.commands.v1     key=siteCode     3p   7 суток    |
  |  fieldstream.telemetry.raw.dlq.v1   key=исходный     1p   14 суток   |
  +----------------------------------------------------------------------+
        ^                        |    |                        ^
        |                        v    v                        |
        |                 +------------------+                 |
        |                 | stream-processor |                 |
        |                 | декодирование,   |                 |
        |                 | алармы, здоровье |                 |
        |                 +------------------+                 |
        |                        |                             |
        |            батч INSERT ON CONFLICT DO NOTHING        |
        |                        v                             |
        |         +--------------------------------------+     |
        |         |  PostgreSQL 16 + TimescaleDB         |     |
        |         |  схемы core и ts, три роли           |     |
        |         |  ts.readings -> _1m -> _1h           |     |
        |         +--------------------------------------+     |
        |                        ^                             |
        |                 SELECT |                             |
        |                        |                             |
        |                  +----------------+                  |
        +------------------| api-gateway    |------------------+
                           | REST + SSE     |
                           +----------------+
                                  ^  |
                       HTTP /api  |  | SSE /api/events
                                  |  v
                           +----------------+
                           |  nginx (web)   |  :8080
                           +----------------+
                                  ^
                             браузер (React 19 SPA)
```

Kafka используется только между сервисами. Сборщик не знает адреса процессора, процессор не знает адреса API. Браузер общается с системой по HTTP и SSE через nginx, то есть в одном origin, без возни с CORS и cookie.

Ни один внутренний сервис не публикует порты наружу: у `edge-collector` и `stream-processor` в compose нет секции `ports` вообще. Граница системы видна прямо в файле, который открывает читатель.

## Границы сервисов

Отдельный процесс заводится, только если у него выполняется хотя бы одно из трёх условий: **своё место запуска**, **свой профиль нагрузки** или **своя зона отказа**.

По этому правилу выделены четыре:

| Сервис             | Почему отдельный                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `device-sim`       | стенд, а не часть продукта, и намеренно ломается                                         |
| `edge-collector`   | стоит в сети площадки, наружу только исходящее соединение к брокеру                      |
| `stream-processor` | масштабируется по числу партиций, обязан уметь переигрывать историю независимо           |
| `api-gateway`      | масштабируется по числу пользователей, его латентность нельзя связывать с приёмом данных |

Не менее важно, что **не** выделено:

- Движок алармов живёт внутри `stream-processor`: у него тот же вход, тот же такт и та же зона отказа. Отдельный сервис добавил бы сетевой вызов и ничего больше.
- Роллапы делает сама база через continuous aggregates. Сервис агрегации не нужен.
- Авторизация живёт внутри `api-gateway`. Приложение одно, обмениваться удостоверениями не с кем.

Четыре сервиса это не мало и не много, это столько, сколько прошло правило.

## Состав сервисов

### device-sim

Заменяет железо. Поднимает 4 Modbus TCP сервера, по одному на линию, обслуживает 24 slave-адреса.

Карта регистров строится **из тех же профилей приборов**, что использует сборщик, и значения кодируются **тем же кодеком**, которым потом декодируются. Благодаря этому round-trip тест ловит ошибку в обе стороны сразу, а новый прибор начинает симулироваться сразу после появления файла профиля.

Физика детерминирована сидом: суточная кривая нагрузки, тепловая модель камеры, цикл оттайки примерно раз в сорок минут, гистерезис компрессора, монотонные счётчики. Значения меняются плавно, шагом заведомо меньше порога фильтра скачков, поэтому фильтр не срабатывает ложно.

Задержка ответа считается по реальному времени кадра на заявленной скорости линии: `delayMs = bytes * 11 / baud * 1000 + turnaround`. Без этого выигрыш блочного чтения остался бы теоретическим, а так он виден на графике длительности цикла.

Отдельный API позволяет вносить неисправности: молчащий прибор, битая контрольная сумма, зависший сокет, исключение протокола, уход значения за шкалу, залипшая дверь, обрыв шлюза целиком.

Это отдельный процесс, а не заглушка внутри сборщика. В боевом коде нет ни одной ветки «если тест», и проверяется весь путь целиком, включая сеть, таймауты и переподключения.

### edge-collector

Единственный сервис, который трогает приборы. На каждую линию ровно один `LineWorker` с бесконечным последовательным циклом: следующий обход планируется только после завершения предыдущего, поэтому очередь опросов не накапливается.

**Три независимых предохранителя от зависания:**

1. Мягкий таймаут запроса, по умолчанию 600 мс.
2. Собственный жёсткий таймаут `timeout * 2 + 250` через гонку промисов. Нужен потому, что клиентская библиотека умеет зависать так, что промис не резолвится никогда. При срабатывании клиент помечается на пересоздание.
3. Сторожевой таймер всего цикла, `max(pollInterval * 6, 5 минут)`, с принудительным разрывом соединения.

**Размыкатель по ключу `линия:адрес`.** После двух отказов подряд источник уходит на редкую пробу: 30 секунд, удвоение, потолок 5 минут. Перед обходом воркер спрашивает, можно ли вообще идти в эту линию. Смысл в том, что один мёртвый прибор иначе съедает таймаут на каждом обходе и растягивает цикл для всех живых соседей.

**Переподключение** с экспоненциальной задержкой от 1 до 30 секунд и джиттером плюс-минус 10 процентов, чтобы линии не синхронизировались между собой. Фактически выбранная задержка публикуется событием, поэтому лестницу задержек можно нарисовать по фактам, а не по формуле.

**При недоступности Kafka опрос не прерывается.** Кадры копятся в ограниченном буфере на пять минут данных, при переполнении отбрасываются самые старые. Терять телеметрию осознанно лучше, чем расти в памяти до отказа процесса.

Сборщик публикует **сырой кадр** и ничего не знает ни про базу, ни про декодирование в физические величины, ни про алармы.

### stream-processor

Единственный писатель телеметрии. Читает сырые кадры, декодирует по версии профиля, зафиксированной в самом кадре, применяет множители и порядок байтов, считает производные метрики, фильтрует резкие скачки, определяет режим камеры, ведёт дерево здоровья, гоняет движок алармов и пишет батчами в гипертаблицы.

Ядро вынесено в чистые функции без ввода-вывода:

```ts
evaluateDeviceAlarms(prev, samples, rules, mode, nowMs);
detectDeviceEvents(prev, curr);
buildHealthTree(nodes, policy, nowMs);
spikeFilter(prevAccepted, candidate, maxDelta, acceptAfter);
```

Ноль побочных эффектов, время приходит аргументом. Именно это делает возможным переигрывание истории: тот же код, другой источник и другой приёмник.

**Дерево здоровья** отдаёт не плоский список «жив или мёртв», а иерархию с машинной причиной статуса: `consecutive_errors`, `stale`, `no_data`, `awaiting_success`, `startup_grace`, `polling_disabled`, `children_offline`.

Правило агрегации у шлюза намеренно отличается от правила у линии. Если все линии шлюза молчат, шлюз получает статус `unknown`, а не `offline`, потому что по молчанию линий нельзя судить о живости самого шлюза. Асимметрия неочевидна, поэтому закрыта отдельным именованным тестом.

Окно `startup_grace` длиной 70 секунд нужно, чтобы после перезапуска дерево не мигало красным: молчание в первые секунды это ещё не авария.

### api-gateway

Всё, что видит браузер: авторизация, права, дерево объектов, история серий, алармы и уставки, шина живых событий, отправка команд приборам.

Телеметрию не пишет вообще: у роли `fs_api` нет прав на вставку в `ts.readings`, и это проверяется интеграционным тестом, а не соглашением.

**Авторизация с разделением токенов.** Access-токен живёт в памяти вкладки, refresh в куке `HttpOnly` с узким путём. В базе хранится не токен, а его хеш с секретной солью. Ротация идёт атомарным обновлением по предыдущему хешу: проигравший гонку запрос получает ноль строк и честный отказ, а не порчу состояния. Окно повтора длиной 60 секунд решает частую беду: если ответ потерялся в сети и клиент повторил тот же refresh, он получает ту же пару токенов, а не разлогинивание. Отдельно различаются «сессия отозвана» и «сервер недоступен»: во втором случае пользователя не выбрасывает.

**Живые события через SSE**, одно соединение на вкладку. Маршрутизация по ключам подписки вида `site:SITE-A`, `device:RC-101`, `topic:pipeline`. Кольцевой буфер последних событий с монотонным идентификатором: при обрыве браузер присылает `Last-Event-ID`, сервер добивает пропущенное. Если идентификатор вышел за пределы кольца или инстанс перезапустился, отправляется явный сигнал рассинхронизации, и клиент делает один полный перезапрос вместо тихой потери данных.

Одна тонкость стоила отладки и потому упомянута здесь: сжатие ответов надо отключать именно для потока событий, причём по исходному URL запроса, потому что к моменту отправки заголовков путь уже обрезан роутером. И на стороне nginx у потока событий должна быть отключена буферизация, иначе события копятся и приходят пачками раз в минуту.

**Единая шкала времени.** Сервер ставит своё время в заголовок каждого ответа, клиент подводит часы с поправкой на время обращения. Весь интерфейс спрашивает «сейчас» только у этого модуля, а правило линтера запрещает обращаться к системным часам напрямую где-либо ещё. Проблема настоящая: при расхождении часов в десять минут свежие данные выглядят протухшими, а протухшие свежими.

## Kafka

### Топики

Все имена, ключи, число партиций и настройки объявлены **один раз** в `packages/contracts/src/kafka/topics.manifest.ts`. Из манифеста выводятся и конфигурация создания топиков, и типы сообщений. Манифест это код, а не документация про код, поэтому разойтись с реальностью он не может.

| Топик                   | Ключ и почему                                                                                                                                                                 | Партиций | Хранение       |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------- |
| `telemetry.raw.v1`      | `deviceCode`. Порядок нужен только внутри прибора. Ключ это стабильный бизнес-код, а не идентификатор из базы: пересоздание базы иначе переразбросало бы приборы по партициям | 6        | 7 суток        |
| `collector.cycles.v1`   | `lineCode`, порядок циклов внутри линии                                                                                                                                       | 3        | 3 суток        |
| `telemetry.readings.v1` | `deviceCode`                                                                                                                                                                  | 6        | 24 часа        |
| `device.state.v1`       | `deviceCode` как идентификатор узла                                                                                                                                           | 3        | компактируется |
| `alarms.events.v1`      | `deviceCode`: важен порядок «поднят, затем снят» внутри прибора, а не глобальный порядок по правилу                                                                           | 3        | 30 суток       |
| `device.commands.v1`    | `siteCode`, команды одной площадке применяются по порядку                                                                                                                     | 3        | 7 суток        |
| `telemetry.raw.dlq.v1`  | сохраняется ключ исходного сообщения, иначе после повторной подачи оно уедет в другую партицию и порядок внутри прибора развалится                                            | 1        | 14 суток       |

В сыром топике едут **сырые слова регистров**, а не готовые значения. Это принципиально: только так историю можно переиграть исправленным декодером.

Топик `telemetry.readings.v1` живёт сутки, потому что это шина живого распределения, а не хранилище. Источник истины по истории это гипертаблица.

Автосоздание топиков выключено. Опечатка в имени переменной окружения здесь молча создала бы топик с одной партицией и тихо сломала всю модель партиционирования.

### Семантика доставки

**At-least-once с идемпотентными эффектами. Транзакции Kafka не используются, и это решение, а не экономия усилий.**

Гарантия «ровно один раз» через транзакции брокера закрывает связку «прочитал, обработал, записал», когда и вход, и выход это топики. Здесь выход это Postgres, транзакция брокера его не покрывает, значит ключ идемпотентности в таблице нужен в любом случае. Раз он всё равно нужен, транзакции добавляют координатора и заметно более сложное восстановление, ничего не убирая. Хуже того, неверно выведенный идентификатор транзакции ломает защиту от зависших писателей и даёт **ложное** ощущение точной доставки, что опаснее честного повтора.

Продюсер идемпотентный, с подтверждением от всех реплик. Идемпотентность продюсера снимает дубли от собственных повторов и, что важнее, сохраняет порядок внутри партиции при включённых повторах.

Консьюмер работает с ручным коммитом. Порядок строго такой:

```
накопить батч (до 500 строк или 200 мс)
  -> BEGIN
  -> multi-row INSERT ... ON CONFLICT DO NOTHING
  -> COMMIT
  -> подтвердить смещения
```

Падение между записью в базу и коммитом смещения даёт повтор, а повтор не даёт эффекта.

**Идемпотентность обеспечена схемой базы, а не логикой приложения:**

| Эффект                  | Ключ идемпотентности                                                        |
| ----------------------- | --------------------------------------------------------------------------- |
| `ts.readings`           | `UNIQUE (device_id, metric_key, ts)`                                        |
| `core.alarm_events`     | `UNIQUE (dedupe_key)`                                                       |
| `core.device_events`    | `UNIQUE (device_id, kind, occurred_at)`                                     |
| `core.applied_commands` | `PRIMARY KEY (command_id)`, команда исполняется только если вставка удалась |
| `core.outbox`           | `UNIQUE (aggregate_id, revision)`                                           |

Порядок гарантируется только внутри партиции, то есть внутри прибора, и этого домену достаточно: два чтения одного датчика никогда не приедут наоборот, поэтому снятие аларма не может обогнать его подъём.

### Отказы

**Классификация ошибки первична, она определяет всё поведение.**

_Транзиентная_ (база недоступна, обрыв соединения): смещение не коммитится, партиция ставится на паузу, задержка растёт экспоненциально, затем работа возобновляется. Если не выправилось, процесс честно завершается с ненулевым кодом и перезапускается.

Отправлять такие сообщения в очередь недоставленных было бы ложью: при десятиминутной недоступности базы она набьётся валидными данными, которые потом никто не разберёт.

_Терминальная_ (не проходит валидацию, неизвестный профиль, кадр не той длины): повторов нет вообще. Сырые байты уезжают в отдельный топик с исходным ключом и полным набором диагностических заголовков, смещение коммитится, поток идёт дальше. Одна битая запись не останавливает партицию.

В очередь недоставленных кладутся **именно сырые байты**, без попытки разбора. Иначе сообщение, которое невозможно разобрать, физически нельзя было бы туда положить.

Отложенных повторов через топики с задержкой здесь нет: они дают больше отладки гонок, чем пользы.

При остановке процесса обязателен корректный выход: дожать текущий батч, подтвердить смещения, отключиться. Без явного отключения группа ждёт истечения таймаута сессии перед перераспределением, и отставание взлетает на тридцать секунд на ровном месте.

### Отставание консьюмера

Считается как разница между концом лога и подтверждённым смещением, отдаётся метрикой и через API. Рядом всегда показывается отставание **в секундах**, потому что в сообщениях оно ни о чём не говорит: тысяча сообщений это много или мало в зависимости от темпа.

Три характерные картины:

- растёт равномерно по всем партициям: не хватает потребителей, добавить инстанс, потолок это число партиций;
- растёт на одной партиции: перекос ключа или застрявший инстанс, лечится разбором конкретного ключа, а не масштабированием;
- пилообразное: проблема не в скорости обработки, а в редких коммитах.

### Эволюция схем

Реестра схем нет. Единственный источник истины это схемы `zod` в общем пакете контрактов.

Типы TypeScript выводятся из тех же схем, поэтому ни один сервис не описывает чужую структуру заново, и фронтенд использует ровно те же определения, что бэкенд. Мажорная версия входит в имя топика, версия и тип схемы едут в заголовках сообщения.

Совместимость стережёт тест, а не сервис: в репозитории лежат замороженные примеры каждой версии, и тест проверяет, что текущая схема их всё ещё принимает. Ломающее изменение валит сборку и обязывает завести новую версию.

Реестр схем с бинарным форматом был бы правильным выбором при появлении потребителя не на TypeScript или при требовании компактности. Пока таких нет, это второй контейнер и заметное усложнение сборки ради нуля пользы.

### Переигрывание истории

Три разные вещи, которые постоянно смешивают, здесь разведены явно:

1. **Догрузка событий в браузере.** Соединение оборвалось на сорок секунд, при восстановлении клиент присылает последний полученный идентификатор, сервер добивает пропущенное. К Kafka отношения не имеет.
2. **Просмотр истории.** Обычный запрос к гипертаблице за прошлое окно. Тоже не Kafka.
3. **Переигрывание из Kafka.** Прогон сырых кадров за выбранный период через изменённый декодер или изменённые уставки.

Третье работает так: поднимается эфемерная группа потребителей, стартовые смещения находятся по времени, чтение идёт до конца лога, затем группа удаляется. Боевая группа не трогается, её смещения не сдвигаются. Обработка идёт через **те же чистые функции**, отличаются два аргумента: профиль или уставки берутся изменённые, а часы подменены на возвращающие время сообщения. Именно из-за инжектированного времени выдержки и гистерезисы отрабатывают корректно на скорости в тысячи раз быстрее реальной.

Результат пишется в теневые таблицы. **Боевая история не переписывается никогда**: сжатые чанки не предназначены для массового переписывания, и попытка это делать стоит дорого без всякой пользы. Исправленная версия профиля применяется к боевой конфигурации с текущего момента.

### Когда Kafka здесь была бы лишней

Честный ответ, потому что вопрос закономерный.

При 24 приборах и потоке около двух сообщений в секунду Kafka избыточна **по нагрузке**. Оправдана она **по свойствам**, и свойств ровно четыре:

1. **Развязка жёсткого такта опроса и медленного потребителя.** Опрос линии идёт с фиксированной каденцией. Если запись в базу тормозит, это не имеет права растягивать обход линии. Kafka здесь буфер с диском.
2. **Один вход, несколько независимых потребителей.** Запись истории (важна пропускная способность), движок алармов (важны порядок и свежесть), живая отдача в браузер (старые сообщения вредны). Это независимые группы над одним логом, каждая со своим смещением.
3. **Переигрывание.** В сыром топике лежат кадры как они пришли с линии. Ошибка в декодере, найденная через неделю, чинится прогоном той же недели через исправленный код. Очередь такого не позволяет: сообщение прочитано и его больше нет.
4. **Топология.** Сборщик стоит в сети площадки и входящих соединений не принимает, поэтому команды приходят ему топиком, а не запросом.

Если бы нужен был только буфер, хватило бы `LISTEN/NOTIFY` в Postgres или Redis Streams. Если бы нужны были несколько потребителей без переигрывания, разумнее был бы NATS JetStream, и стек стал бы легче на гигабайт памяти. Kafka оправдана именно сочетанием всех четырёх свойств.

## Модель данных

Одна база, две прикладные схемы и три роли с минимальными правами. Отдельные базы на сервис не заводятся: расширение TimescaleDB ставится на базу, три базы означают три установки расширения и лишний вес, а изоляция достигается правами.

### Роли

```sql
cw_migrator  -- владелец схем, только миграции
fs_ingest    -- stream-processor, вставка телеметрии
fs_api       -- api-gateway, чтение
```

У роли `fs_api` **нет** права вставки в `ts.readings`, и на это есть интеграционный тест, ожидающий отказа в доступе. Проверяемая граница лучше, чем договорённость о границе.

### Гипертаблицы

```sql
CREATE TABLE ts.readings (
  ts          timestamptz      NOT NULL,
  device_id   int              NOT NULL,
  metric_key  text             NOT NULL,
  value       double precision,
  quality     smallint         NOT NULL DEFAULT 0
);
SELECT create_hypertable('ts.readings','ts', chunk_time_interval => INTERVAL '1 day');

CREATE UNIQUE INDEX readings_pk ON ts.readings (device_id, metric_key, ts DESC);

ALTER TABLE ts.readings SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'device_id, metric_key',
  timescaledb.compress_orderby   = 'ts DESC'
);
SELECT add_compression_policy('ts.readings', INTERVAL '2 days');
SELECT add_retention_policy  ('ts.readings', INTERVAL '30 days');
```

Уникальный индекс обязан включать колонку партиционирования, и он же служит ключом идемпотентности при вставке.

**Узкая форма таблицы выбрана осознанно.** Две модели приборов имеют разный набор метрик, широкая таблица требовала бы изменения схемы на каждую новую метрику. При одной жёсткой схеме прибора широкая таблица была бы быстрее, и это честный компромисс, а не универсально правильный выбор.

**Разбиение по пространству не включено.** Выигрыш оно даёт на кластере из нескольких узлов, на одном узле это лишняя сложность без эффекта.

**Инвариант, который снимает всю боль со сжатыми данными:** живая запись всегда идёт в горячий чанк, политика сжатия стоит на двух сутках, переигрывание пишет в несжимаемую теневую таблицу, история не переписывается. Следовательно ни одна операция записи не попадает в сжатый чанк, и вопрос о поведении вставки по сжатым данным просто не возникает.

### Непрерывные агрегаты

Хранятся **сумма и количество, а не среднее**. Среднее от средних неверно при разном числе замеров в интервале, и без суммы с количеством верхний уровень нельзя построить корректно. Это ровно то место, где обычно ошибаются.

Агрегаты иерархические: часовой строится **над минутным**, а не над сырой таблицей.

Пять правил, каждое из которых стоило бы отладки, если бы не было выписано заранее:

1. У каждого уровня своя политика обновления. Без неё верхний агрегат не материализуется сам.
2. Ширина интервала родителя кратна интервалу потомка.
3. Отступ от конца у родителя строго больше, чем у потомка, иначе родитель считает по недоматериализованным данным.
4. Режим реального времени на нижнем уровне обязателен, иначе последняя минута пропадает с живого графика.
5. Срок хранения сырой таблицы не залезает в окно, которое ещё обновляют политики агрегатов.

### Правило выбора источника

```
окно <= 6 часов   -> ts.readings (сырые)
окно <= 7 дней    -> минутный агрегат
иначе             -> часовой агрегат
```

Поверх всегда накладывается группировка по интервалу `окно / maxPoints` с жёстким пределом в 2000 точек. Ответ содержит сведения о том, откуда взяты данные и какой шаг, и интерфейс показывает это подписью над графиком.

Функция выбора лежит в общем пакете контрактов и доступна и серверу, и браузеру, поэтому подпись под графиком не может разойтись с тем, откуда данные пришли на самом деле.

Это закрывает сразу две типичные беды: эндпоинт без ограничения, отдающий всю историю, и интерфейс, перезапрашивающий всё окно чаще, чем данные вообще меняются.

### Объём

| Что                             | Оценка                                                          |
| ------------------------------- | --------------------------------------------------------------- |
| живая запись                    | 24 прибора на ~10 метрик каждые 10 с, около 2 млн строк в сутки |
| несжатые                        | около 350 МБ в сутки                                            |
| сжатые, начиная со вторых суток | около 25-35 МБ в сутки                                          |
| при хранении 30 суток           | около 1.7 ГБ                                                    |
| том Kafka                       | около 0.7 ГБ                                                    |

### Миграции

Чистый SQL, каждая с прямым и обратным направлением. Применяются одноразовым контейнером до старта сервисов, а не при старте приложения, иначе две реплики процессора гонятся за одну миграцию. Перед работой берётся блокировка уровня базы.

ORM описывает только запросы и типы и **не владеет схемой**: DDL TimescaleDB ни один ORM нормально не выражает, и попытка это натянуть кончается ручными обходными путями.

## Фронтенд

React 19, TypeScript в строгом режиме, Vite. MUI для каркаса, SCSS-модули по БЭМ для собственных стилей, uPlot для временных рядов, TanStack Query для серверного состояния.

**uPlot вместо более привычного Chart.js** потому, что график за неделю это десятки тысяч точек: uPlot рисует их на canvas за единицы миллисекунд и весит около 45 КБ. Chart.js остался бы правильным выбором, если бы графиков было три штуки по двести точек.

### Состояние

Серверное состояние живёт только в TanStack Query, Redux нет. Локальное состояние на `useState`, а как только в компоненте набирается два и более связанных значения, вместо них `useReducer`. Глобального минимум: токен доступа в памяти вкладки, поправка часов, состояние соединения.

**Живые данные не инвалидируют кэш.** Событие точечно патчит закэшированные данные, к сети запрос не идёт. К сети идёт только при явном сигнале рассинхронизации. На это есть тест, который проверяет, что сетевого запроса не произошло.

Поток телеметрии дросселируется **на сервере** до одного обновления в секунду на прибор независимо от частоты опроса: браузер не должен получать больше, чем способен отрисовать.

### Экраны

1. **Обзор.** Дерево объектов с агрегированным статусом и машинной причиной. Плитка показывает **прочерк**, а не последнее известное число, если состояние старше порога: устаревшие данные не выдаются за измеренные.
2. **Прибор.** Живые значения, график с выбором окна и подписью источника, полоса режимов под графиком (видно, что рост температуры совпал с оттайкой), панель уставок с переключением режима, журнал изменений уставок. Отдельно карта регистров: ось адресов, параметры как блоки, склеенные блоки нарисованы скобками, переключатель режима плана меняет число запросов и фактическую длительность цикла на глазах.
3. **Алармы.** Живая лента, история с курсорной постраничной навигацией, подтверждение с оптимистичным обновлением и откатом при ошибке.

### Качество интерфейса

У каждого экрана честные состояния: загрузка (скелетоны фиксированной высоты, а не спиннер на всю страницу), пусто, ошибка (с различением «сервер недоступен» и «сессия отозвана»), устаревшие данные, недоступность живого канала.

Адаптивность на трёх контрольных ширинах, таблицы в контейнере с горизонтальной прокруткой, устойчивые размеры у панелей инструментов. Доступность: управление фокусом в модальных окнах, навигация с клавиатуры по таблице, объявление новых событий для программ чтения с экрана.

### Построитель плана чтения

Самый содержательный кусок предметной логики, поэтому описан отдельно.

План превращает описание прибора в минимальный набор запросов. Соседние адреса одного типа регистров склеиваются в блочное чтение по правилу **«только вплотную»**: разрыв даже в один регистр рвёт блок. Поэтому автоматически собранный блок **никогда не читает регистр, который не нужен ни одному параметру**.

Учитываются предел в 125 регистров на запрос (ограничение протокола), явно объявленные блоки, требование, чтобы параметр помещался в блок целиком (32-битная величина не может быть разорвана между запросами), запрет перекрытий и запрет блоков, не покрывающих ни одного параметра.

На реальных профилях это даёт **3 запроса вместо 9** на счётчике и **4 вместо 9** на контроллере. Есть и режим «по запросу на параметр», нужный для наглядного сравнения.

Ключевой тест здесь не на числа, а на инвариант: **значения, прочитанные по склеенному плану, побайтово совпадают со значениями, прочитанными по наивному**. Именно он делает оптимизацию безопасной, а не просто быстрой.

### Границы зависимостей

Стерегутся тремя эшелонами:

1. **Компилятор.** Ссылки между проектами перечисляют только разрешённые пакеты, поле `exports` без подстановок закрывает глубокие импорты во внутренности чужого пакета.
2. **Линтер.** Зоны запрещённых импортов: в контрактах нельзя ничего серверного, потому что пакет обязан собираться в браузерный бандл; в доменной логике нельзя базу и брокер.
3. **Тест.** Проверка направления зависимостей запускается обычным тестом, а не отдельным шагом сборки, поэтому падает так же громко, как упавшая бизнес-логика, и её нельзя заглушить построчным отключением правила.

## Docker

Цель: `git clone`, копирование файла окружения, одна команда, и система работает с непустыми графиками без единого ручного шага.

Порядок старта задан условиями готовности, без единой задержки «на всякий случай»:

```
timescaledb (готова) + kafka (готова)
   -> создание топиков + миграции (завершились)
      -> засев истории
      -> device-sim (готов) -> edge-collector
      -> stream-processor -> api-gateway -> web
```

Что видит человек в первые полторы минуты:

| Время   | Что происходит                                                                                       |
| ------- | ---------------------------------------------------------------------------------------------------- |
| 0-15 с  | поднимаются брокер и база, создаются топики, катятся миграции                                        |
| 12 с    | страница уже открывается и показывает панель готовности со стадиями, а не пустой экран и не ошибку   |
| 15-45 с | засевается неделя истории в минутном разрешении                                                      |
| 20 с    | стартует сборщик, дерево здоровья появляется целиком в состоянии `startup_grace` с обратным отсчётом |
| 45 с    | графики нарисованы по засеянной истории, пустых осей не бывает                                       |
| 90 с    | окно ожидания истекает, дерево зеленеет, идут настоящие события                                      |

В историю заранее засеяны три происшествия: двухчасовое молчание прибора, оставленная открытой дверь и перегрев с алармом. Без готовых происшествий список алармов и навигация по истории пусты и бессмысленны в первую минуту.

Ни один сервис не уходит в цикл перезапуска при недоступной Kafka: сервисы повторяют попытки с возрастающей задержкой и честно сообщают, что ещё не готовы.

Образ собирается многостадийно: слой зависимостей отделён от слоя кода, поэтому правка одной строки не пересобирает зависимости. Итоговый образ содержит только рабочие зависимости, без инструментов сборки. Контейнеры работают не от суперпользователя. Проверка живости сделана скриптом на Node, а не через `curl`, которого в минимальном образе нет.

Ни одного значения по умолчанию для секретов: отсутствие обязательной переменной окружения это падение на старте с внятным списком, а не тихая работа с известным всем значением.

## Тестирование

Тестируется то, где ошибка стоит дорого и где логика нетривиальна. Процент покрытия не самоцель.

### Чистые функции

Быстрые, без базы и брокера, и именно они ловят регрессии в содержательной части.

- **Построитель плана чтения.** Табличные случаи: склейка только вплотную, разрыв рвёт блок, предел в 125 регистров, параметр не помещается в блок целиком, перекрытие объявленных блоков, регистры разных типов не склеиваются. Плюс порождающий тест со случайными профилями, проверяющий инварианты: каждый параметр покрыт ровно одним блоком, блоки не пересекаются, при нулевом допустимом разрыве не читается ни одного лишнего регистра, а значения по склеенному плану совпадают со значениями по наивному.
- **Кодек.** Кодирование и декодирование по всем сочетаниям типа и порядка байтов, отрицательные значения, обратный порядок слов у счётчика, множители и точность, битовые маски, перечисления.
- **Алармы.** Гистерезис (не дребезжит ровно на границе), выдержка, смена режима меняет применимую уставку, заглушенные режимы, снятие аларма при удалении уставки, отсутствие значения не влияет на счётчик.
- **Дерево здоровья** как автомат: все машинные причины, окно после старта, асимметрия агрегации у шлюза отдельным именованным тестом.
- **Размыкатель и задержки:** два отказа уводят источник на пробу, успех сбрасывает, джиттер не вырожденный и укладывается в границы, жёсткий таймаут срабатывает на промисе, который никогда не завершается.

Все переходы состояний проверяются **без реального ожидания**: время инжектируется.

### Контрактные

Каждая схема сообщения разбирает свой замороженный пример, поэтому ломающее изменение падает здесь. Отдельно проверяется, что пакет контрактов не имеет посторонних зависимостей времени выполнения, и что направление зависимостей между пакетами не нарушено.

### Интеграционные

На настоящих Kafka и TimescaleDB в контейнерах. Их немного, но каждый доказывает конкретное утверждение:

1. Повторная доставка того же батча не меняет число строк.
2. Процесс убит посреди батча, после перезапуска продолжает с подтверждённого смещения, дублей нет.
3. Неразбираемое сообщение уезжает в очередь недоставленных сырыми байтами, партиция не блокируется.
4. Повторная подача возвращает сообщение в **ту же** партицию.
5. Кратковременная недоступность базы даёт паузу и полное восстановление без потерь.
6. Часовой агрегат даёт те же значения, что прямой запрос по сырой таблице.
7. Роль интерфейса не может писать в таблицу телеметрии.

### Что сознательно не тестируется

Контроллеры с подменёнными сервисами и проверкой «подмена была вызвана»: такой тест проверяет, что код написан так, как написан. Подмена брокера в модульных тестах: она проверяет подмену, а не брокер. Снимки целых страниц. Тривиальные преобразования и конфигурация.

## Решения и компромиссы

Записи о решениях лежат в `docs/adr` в формате «контекст, решение, последствия, отвергнутые альтернативы».

```
0001 Монорепа на pnpm вместо публикации пакетов по тегам
0002 Kafka как шина между площадкой и ядром, условие пересмотра
0003 Схемы zod в общем пакете вместо реестра схем
0004 At-least-once с идемпотентностью вместо транзакций брокера
0005 TimescaleDB, узкая схема, одна база со схемами и ролями
0006 Иерархические непрерывные агрегаты: сумма и количество, правила отступов
0007 SSE с кольцевым буфером вместо WebSocket
0008 ORM для запросов, SQL для схемы: ORM не владеет схемой
0009 Правило выделения сервиса и почему алармы не отдельный сервис
0010 Переигрывание не переписывает историю
0011 uPlot вместо Chart.js
```

Компромиссы, которые стоит назвать прямо:

- Кольцевой буфер событий живёт в памяти инстанса, поэтому при нескольких инстансах нужны либо липкие сессии, либо явный сигнал рассинхронизации, который здесь и сделан.
- Сборщик при недоступном брокере отбрасывает самые старые кадры вместо роста в памяти. Это осознанная потеря данных в обмен на выживание процесса.
- Одна реплика брокера в демо-конфигурации означает, что его потеря это потеря данных. Что изменится на трёх, описано отдельно.

## Чего здесь сознательно нет

Осознанный отказ полезнее молчания, поэтому список приводится целиком.

| Не сделано                                                   | Почему                                                                                    |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| Реестр схем с бинарным форматом                              | второй контейнер и постоянные ограничения ради нуля потребителей не на TypeScript         |
| Транзакции Kafka и точная доставка                           | выход системы это база, идемпотентность приёмника нужна в любом случае                    |
| Отложенные повторы через топики с задержкой                  | больше отладки гонок, чем пользы; заменено классификацией ошибок                          |
| Кластер из нескольких брокеров                               | перераспределение партиций показывают два инстанса потребителя, это дешевле               |
| Свой инспектор Kafka                                         | дублирует готовые инструменты, которые поднимаются профилем compose                       |
| Свой стек Modbus с разбором кадров                           | нулевая релевантность задаче, готовая библиотека решает это сразу                         |
| Prometheus и Grafana в базовом составе                       | метрики отдаются, но два контейнера ради панели не оправданы на ноутбуке                  |
| Kubernetes и шаблоны развёртывания                           | проект про приложение, а не про кластер; манифесты, которые никто не запустит, бесполезны |
| Kafka Streams и подобное                                     | оконная логика написана руками, и поэтому понятно, что у неё внутри                       |
| Отдельная база на каждый сервис                              | на четырёх сервисах даёт тройной расход памяти; изоляция достигается схемами и правами    |
| Отдельные сервисы алармов, агрегации и авторизации           | ни один не проходит правило выделения процесса                                            |
| Событийное хранение состояния и разделение команд и запросов | нет задачи, которая их требует                                                            |
| Распределённая трассировка                                   | сквозной идентификатор запроса в заголовках и логах даёт большую часть пользы малой ценой |
| Мобильное приложение, серверный рендеринг, локализация       | приложение за авторизацией, поисковая индексация не нужна, интерфейс на одном языке       |
